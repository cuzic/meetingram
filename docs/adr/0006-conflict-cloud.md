# ADR 0006: 議論グラフから対立解消図を作る（TOC の図の共通の仕組みを含む）

- Status: Accepted
- 日付: 2026-11-25
- 関連: [ADR 0001 — 議論グラフ](0001-discussion-graph.md)、[ADR 0002 — Windows E2E](0002-e2e-scripted-backends.md)、
  [ADR 0004 — svg-diagram で議論を図解する](0004-svg-discussion-map.md)、[ADR 0007 — CRT](0007-current-reality-tree.md)、
  svg-diagram の `cloud` 部品（v0.10.0）

## 背景

meetingram の目的は、議論を図にして、次に何を聞くべきかを支援すること（`AGENTS.md:3`）。
ADR 0004 で議論マップ（IBIS の問い・案・賛否のマインドマップ）を描けるようになった。TOC の図（CRT・対立解消図）は
ADR 0004 が別の ADR に回した。

- 議論グラフ（ADR 0001 §1）は、`issue`・`position`・`argument`・`decision`・`action` のノードと、
  `responds_to`・`supports`・`objects_to`・`resolves`・`assigns`・`sub_issue_of` のエッジを持つ。どのノードにも根拠の発話がある。
- 「案が対立する問い」は ADR 0001 §2 で既に定義している（`responds_to` する position が 2 件以上ある、または
  `objects_to` を受けた position が付いている）。整理の段 1 は、この問いを必ず議題として残す。
- 対立解消図（evaporating cloud）は、共通の目的 A、要望 B・C、対立する行動 D・D2、各矢印の裏にある前提と、
  前提を崩す打ち手（injection）でできている。D・D2 は対立する 2 つの案、B・C は各案を支える理由にあたるので、
  グラフに材料の多くがある。**A と前提は会議でほとんど口にされない**ので、グラフには無い。
- svg-diagram v0.10.0 は `cloud` 部品を持つ。入力は `a`・`b`・`c`・`d`・`d2`（各 120 文字まで）、
  `assumptions`（`on` は `ab`・`ac`・`bd`・`cd`・`dd`、`text`、任意の `injection`。12 件まで）、`conflictLabel`。
  箱ごとの tone や札は持たない。
- ADR 0004 のアダプター（`apps/desktop/diagram-renderer/renderer.ts`）は `version: 1` の `root` だけを受け、`mindmap` だけを描く。
  Rust 側の SVG の許可リスト（`apps/discussion-diagram/src/lib.rs` の `valid_svg`）は議論マップの出力に合わせてある。

## 決めること / 決めないこと

- 決めること:
  - 対立解消図の題材（どの問いの、どの 2 案）の選び方
  - LLM に足させるもの（A・B・C・前提・打ち手）と、その入出力・検証
  - **推測の扱い**（発言に根拠のある要素と、LLM が推測した要素の区別と見せ方）。ADR 0007（CRT）も同じ規則を使う
  - **分析の保存と呼び出しの仕組み**（ボタンで 1 回呼ぶ、結果を保存する、古くなったら知らせる）。ADR 0007 も同じ仕組みに乗る
  - 描画（アダプターの契約の拡張、許可リスト、表示と保存）
- 決めないこと:
  - CRT（ADR 0007）
  - 前提を「次に聞く問い」としてヒントに出すこと（ヒントの ADR。この ADR は図の下に一覧を出すだけ）
  - 対立解消図の人による編集（文言の書き換え、前提の追加）。v1 は作り直しと削除と、推測の要素に根拠の発話を付けること（§8）だけ
  - 会議をまたいだ対立の追跡（ADR 0001 の Q4）
  - macOS（ADR 0001 と同じく、文字起こしが無いので出さない）

## 選択肢

### 題材の選び方

#### S1. グラフから決定的に候補を選び、利用者が 1 つ選ぶ（採用）
- 仕組み: 生きている案が 2 件以上ある問い（ADR 0001 §2 の「案が対立する問い」のうち、案が 1 件だけのものを除く。§4）を純粋関数で数え上げ、一覧にする。利用者が問いを選び、
  案が 3 つ以上なら 2 つを選ぶ（既定は、賛否の理由が多い順の上位 2 つ）。
- 良い点: LLM を呼ぶ前に、題材が人に見える。同じ入力なら同じ候補になる。費用は押した分だけ。
- 悪い点: 案として抽出されていない対立（「品質も大事だが納期も」と一人が語る板挟み）は拾えない。

#### S2. LLM に会議全体から対立を探させる
- 良い点: S1 が拾えない板挟みも拾える。
- 悪い点: 呼び出しが 1 回増え、何が題材になるかが LLM 次第になる。グラフの承認・却下（ADR 0001 §5）と結び付かない。
  S1 で足りない会議が多いと分かってから足す。

### 推測の持ち方

#### I1. 要素ごとに `basis` を持たせ、根拠を検証する（採用）
- 仕組み: LLM は各要素に `basis: "stated" | "inferred"` を付ける。`stated` は、入力に載せた発話の `uid` か
  グラフの `nid` を 1 つ以上根拠に持つ。根拠が検証で 1 つも残らない `stated` は `inferred` に格下げする（落とさない）。
- 良い点: Q1 のとおり推測も出しつつ、発言と推測を機械的に見分けられる。根拠から発話に戻れる（ADR 0001 の方針）。
- 悪い点: LLM が `inferred` を `stated` と偽っても、根拠の `uid` が入力にあれば通る（中身の一致までは見ない）。
  spike で、`stated` の根拠が実際にその内容を述べているかを数える。

#### I2. 推測を許さない
- Q1 で owner が退けた。A と前提がほぼ空になり、図の形にならない。

### 保存

#### P1. コアの `discussion-graph` に分析の表を 1 つ足す（採用）
- 仕組み: `graph_analyses` に、セッション・種類・題材の鍵ごとに最新の 1 件を保存する（§2）。グラフの表は変えない。
- 良い点: 1 回 10〜60 秒かかり費用もかかる呼び出しの結果を、履歴を開き直すたびに払い直さない。
  作り直し（ADR 0001 §3）でグラフと一緒に消せる。表を足すだけなので移行の仕組みは要らない（ADR 0001 §1）。
- 悪い点: コア PR → タグ → アプリ PR の順になる。

#### P2. 議論グラフのノードとエッジとして足す
- 仕組み: `objective`・`assumption` などのノードの種類を足し、増分・整理・承認と同じ経路に乗せる。
- 悪い点: 前提は「矢印の裏」にあり、ノード同士のエッジに素直に乗らない。推測のノードは根拠の発話を持たず、
  ADR 0001 §2 の「根拠の無い操作は落とす」と衝突する。整理（merge）が推測のノードを巻き込み、S2 で合わせた抽出の質が動く。

#### P3. 保存しない（画面を閉じたら消える）
- 悪い点: 履歴を開くたびに LLM を呼び直す。結果が呼ぶたびに変わり、前に見た図が戻らない。

## 決定

**S1・I1・P1 を採る。** 以下が詳細。§1〜§3 と §6 は TOC の図の共通の仕組みで、ADR 0007（CRT）も使う。

### 1. 推測の印（共通）

- 図の各要素は `basis` を持つ。`stated`（発言に根拠がある）と `inferred`（LLM の推測）の 2 値。
- `stated` の要素は、その回の入力に載せた**発話**の `uid`（`grounds`）を 1 つ以上持つ。`nids`（グラフのノード）は関係を示すだけで、
  `stated` の根拠にならない（round 1 の M3。題材の nid を挙げるだけで A や前提を `stated` にできる抜け道を塞ぐ）。
  検証で入力に無い `uid` と `nid` を落とし、`grounds` が 1 つも残らなければ `inferred` に格下げし、格下げの件数を記録する。
- `stated` を付けられるのは LLM の出力だけではない。アプリがグラフから写した要素（対立解消図の D・D2）は、写したノードの根拠の
  発話を `grounds` に持つ `stated` とする。人が `inferred` の要素に入力の発話を 1 つ付けたものも `stated` で、`by: "user"` を持つ（§8）。
- `inferred` の要素は根拠を持たなくてよい。関係するノードを `nids` に持ってよい（表示で「この案から推測」と示すため）。
- 残る穴: 入力にある発話の `uid` なら、内容が合わなくても `stated` で通る。根拠の発話を画面で開けるので人が確かめられることと、
  spike の (4) で頻度を測ることで扱う。そのため、根拠の発話は入力から外さない（§4、ADR 0007 §2）。
- 画面では、推測の要素を発言と見分けられるようにする。描画の手段は図種ごとに §4 と ADR 0007 で決める。
  図の下の凡例に「推測: 会議では述べられていない。LLM が補った」と書く。
- 推測の要素は確信度を持たない（推測に自己申告の確信度を付けさせても、確からしさを確かめる手段が無いため）。

### 2. 分析の保存（共通。コア）

`discussion-graph` の接続（ADR 0001 の P）に表を 1 つ足す:

```
graph_analyses
  session_id, kind TEXT ('cloud' | 'crt'), subject TEXT,
  based_on_rev INTEGER        -- 入力に使ったグラフの rev
  body_json TEXT              -- 検証済みの結果（§3 の形。本文を含む）
  provider_model TEXT, dropped INTEGER, downgraded INTEGER, created_at
  revision INTEGER            -- 行を書くたびに進める（§8。r6 で追加）
  PRIMARY KEY (session_id, kind, subject)
```

- `subject` は題材の鍵。対立解消図は `"{issue_nid}:{position_nid}:{position_nid}"`（position の nid は文字列の昇順）。
  CRT は ADR 0007 で決める。
- 作り直すと同じ鍵の行を置き換える（最新の 1 件だけを持つ）。利用者が削除できる。
- `GraphStore::delete_session`（グラフの作り直し）は、同じトランザクションでこの表の行も消す。
- 保存の関数は 1 回の `db()` の中で呼ぶ（§3 の「完了の照合」）。
- 書き込みは `BEGIN IMMEDIATE` の短いトランザクション 1 つ（ADR 0001 §7）。LLM の呼び出しはトランザクションの外。
- 本文は DB にだけ置き、ログに出さない（ADR 0001 §8）。

### 3. 呼び出し（共通。アプリ）

- **起動の条件**: グラフと同じ（`graph_enabled` が有効、Windows、バックエンドを組み立てられる、codex CLI でない。ADR 0001 §3）。
  満たさなければボタンを無効にし、理由を出す。
- **ボタンを押したときだけ呼ぶ**（Q2）。録音中のセッションでも押せる。
- **グラフの読み方**: ADR 0004 の「操作と更新」と同じく、`GraphStore::load_graph` を既存の `db()` 経由で読み、
  読み取りの前後で世代と再構築中かを照らし合わせる。グラフの実行者のロック（LLM の呼び出し中も持たれうる）は取らない。
  分析はグラフの表に書かないので、会議中の増分抽出と並んで動いてよい。
- **同時に動く分析は、アプリ全体で 1 つまで**。動いている間はボタンを無効にし、「作成中」と出す。
- **LLM の呼び出し**: `Summarizer::complete`（ADR 0001 §2）。モデルは `graph_model`、空なら要約のモデル。
  入力の上限は 24,000 文字（ADR 0001 §2 と同じ）。時間の上限は 120 秒（整理と同じ）。超えたらプロセスツリーごと止める（ADR 0001 §2）。
- **応答の読み方**: ADR 0001 §2 と同じく寛容に読み、読めなければエラーの種類を添えて 1 回だけ再試行する。
  それでも駄目なら失敗にし、何も保存しない。
- **完了の照合と保存は 1 回の `db()` の中で行う**（round 1 の M1）。作り直しは、`delete_session` と世代を進める処理を
  1 回の `db()` の中で行っている（`graph_consumer.rs` の `PostMeeting::Rebuild`）。`db()` は `GraphStore` の Mutex を持って動くので、
  分析の保存も同じく 1 回の `db()` の中で「控えた世代と今の世代（`revisions`）が同じで、再構築中でない」ことを確かめてから書く。
  違えば書かずに結果を捨てる。こうすると、作り直しの前に入力を読んだ分析が、作り直しの後の表に書かれることは無い
  （作り直しは nid と rev を振り直すので、書かれると別のノードの図が新しいものとして出てしまう）。
  作り直しの間（`rebuilding`）は分析のボタンを無効にする。保存の後、画面は保存した行を読み直して描く。
- **古さの表示**: 開いたときに `based_on_rev` が今の `rev` より古ければ「グラフが進んでいます（作り直す）」と出す。
  自動では作り直さない（Q2）。題材が消えていたら「題材がなくなりました」と出し、図は出したまま削除を勧める。
  消えたとみなすのは、対立解消図では題材の issue か 2 つの position のどれかが生きていない（`rejected`・`merged`、position は `retracted` も）とき、
  CRT では選んだ議題のどれかが生きていないとき（round 1 の m3）。
- **失敗したとき**: 失敗は分析の画面の文言（種類ごとの固定文）になるだけで、録音・文字起こし・グラフの抽出を止めない。
  ログに出すのは ADR 0001 §8 の「出してよいもの」と、落とした件数・格下げの件数だけ。

### 4. 対立解消図の題材と入力

**候補**（コアの純粋関数 `conflict_candidates(&Graph)`）:
- 生きている issue（`merged`・`rejected` でない）で、生きている position（`rejected`・`merged`・`retracted` でない）が
  生きている `responds_to`（`review = rejected` でない）で 2 件以上付いているもの。
- ADR 0001 §2 の「案が対立する問い」には「`objects_to` を受けた position が 1 件だけ付いている問い」も入るが、候補にしない（round 1 の m2）。
  対立解消図は対立する 2 つの行動（D・D2）を要し、案が 1 件だと D2 を「その案を採らない」と作ることになり、推測が D2 にまで広がるため。
  利用者から求めがあれば別に足す。賛否の理由を数えるときも、却下されたエッジと生きていない argument は数えない。
- 並び順: 決定の無いもの（ADR 0004 の「検討中」）→ 決定済みのもの。同じ組の中は、`objects_to` を受けた position があるもの、
  2 案に付く `supports`・`objects_to` の合計が多いもの、`created_rev` の古いもの、の順。
- 各候補には、案の組の既定（賛否の理由が多い順の上位 2 つ。同数は `created_rev` の古い順）を添える。

**入力**（user。system は固定の指示とスキーマだけ）:
- 題材の issue の本文と、A の手がかりとして、同じ会議のほかの議題（親を持たない issue）の本文を `created_rev` の古い順に最大 5 件、各 60 文字まで
  （round 1 の n2。案が対立する問いは ADR 0001 §2 で必ず議題になり、親を持たないので、親の本文は手がかりにならない）。
- D・D2 にする 2 つの position の本文と nid。
- 各 position に `supports` / `objects_to` で付く argument（たどるのは 2 段まで）の本文・種類・nid。
- 題材の issue に付く decision と action の本文（決定済みのとき）。
- 上のノードの根拠の発話（`uid`、話者ラベル、本文。1 件 200 文字に切り詰め）。上限を超えるときは、
  根拠の発話を 1 ノード 1 件 → 1 件 100 文字 → ほかの議題の本文を外す → 2 段目の argument（とその根拠）を外す、の順に削る
  （A の手がかりより題材の中身を残す。round 2 の n1）。
  根拠の発話は全部は外さない（§1 の `stated` の根拠が無くなるため。round 1 の M3）。ノードの本文は削らない。
  それでも上限を超えるなら LLM を呼ばず、「この問いは図にするには大きすぎます」と出す（round 1 の m1）。
- 会議全体の文字起こしは渡さない（送る量を、題材に関係する発話に絞る）。

### 5. 対立解消図の出力と検証

出力: JSON 1 つ。

```json
{"a":  {"text": "…", "basis": "inferred", "nids": ["n3"]},
 "b":  {"text": "…", "basis": "stated", "grounds": ["u12"], "nids": ["n7"]},
 "c":  {"text": "…", "basis": "inferred"},
 "d":  {"text": "…"},
 "d2": {"text": "…"},
 "assumptions": [
   {"on": "bd", "text": "…", "basis": "stated", "grounds": ["u15"],
    "injection": {"text": "…", "basis": "inferred"}}
 ]}
```

- 検証の後、アプリが保存する本文には §8 の `input_uids`（最上位）と、`inferred` の要素の `related` が加わる。人が根拠を付けた要素は `by: "user"` を持つ。
- `d`・`d2` は、選んだ 2 つの position を短く言い直したもの。`basis` は常に `stated` で、根拠は position の根拠の発話と nid（アプリが付ける。§1）。
  `d` は nid の昇順で先の position、`d2` は後の position にする（題材の鍵と同じ順。作り直しても入れ替わらない。round 1 の n3）。
  入力もこの順に並べ、LLM には入れ替えさせない。
- 書き方の規則（system）: A は B と C の両方が仕える目的で、到達したい状態として書く（問いを決めること自体や、B が確かめたい中身にしない）。
  B は D で満たしたい要望、C は D2 で満たしたい要望で、行動ではなく要望として書く。B は D2 では満たせないもの、C は D では満たせないものにし、
  両方の案で満たせる要望は A に上げる。前提は「…だから B には D が要る」の「…」にあたり、偽でありうる信念として書く
  （矢印の言い直し、箱の語を使っただけで真になる文、決める時期の話にしない）。D への反論は cd、D2 への反論は bd の前提の材料にする
  （その矢印の理由になるときだけ）。dd は必ず 1 件書き、2 案を同時にできない具体的な理由（同じ場所・時間・人・お金を使う、など）を書く。
  会議で述べられた理由があればそれを `stated` にし、無ければいちばんありそうな理由を `inferred` で書いて、両立させる方法を打ち手にする
  （「両方はできない」とだけ書く文、対立を打ち消す文、会議について述べる文にしない）。打ち手は、その前提の制約を外す変更。
  `basis` は役割と関係なく、入力の発話がその中身を述べているかだけで決める（§1。spike の r3・r4 の結果、r6 で改めた）。
  案を出した人が述べた利点・心配・反論も、要素の中身を名指ししていれば根拠になる（§「計測」の読み方 U）。
- 検証（コアの純粋関数。不正な部分だけを落とす）:

| 対象 | 落とす・直す条件 |
| --- | --- |
| 全体 | JSON として読めない、`a`・`b`・`c` のどれかが無い・空 → 失敗（何も保存しない） |
| D・D2 | LLM の `d`・`d2` は本文だけを読み、`basis`・`grounds`・`nids` は読まない。表のほかの行をすべて適用した**後に**、アプリが `basis: stated`、position の根拠の発話（`grounds`）と nid（`nids`）を付ける。LLM の本文は 116 単位で切る（round 3 の M1）。本文が無い・空なら、position の本文を 116 単位で切って使う（round 2 の M1。`cloud` は d・d2 を必須とし、推測の印も付けない） |
| 各要素 | 本文が空 → 落とす（`a`・`b`・`c` なら全体が失敗）。116 を超える → 116 で切る（下の注）。`basis` が未知 → `inferred` |
| 根拠 | `grounds` の `uid` がその回の入力に無い、`nids` がその回の入力に無い → その根拠だけ落とす。`stated` で `grounds` が 1 つも残らない → `inferred` に格下げ（`nids` だけ残っても格下げ。§1） |
| 前提 | `on` が 5 値の外 → 落とす。同じ `on` に 3 件目以降 → 落とす。全体で 8 件を超える → 9 件目以降を落とす |
| 打ち手 | 本文が空 → 打ち手だけ落とす |

- 表は上の行から順に、要素ごとに適用する（全体 → 各要素 → 根拠 → 前提 → 打ち手 → 最後に D・D2）。「各要素」と「根拠」の行は D・D2 には当てない。前提の件数の上限は、`on` の検査と本文の検査で落とした後に、出てきた順で数える。
- **長さの注**（round 1 の M2）: svg-diagram の `cloud` の上限は 120 で、JS の文字列の長さ（UTF-16 の単位）で数える *(未確認。fixture で確かめる)*。
  推測の要素には描画のときに「〔推測〕」（4 単位）を前に付ける（§6）ので、検証では本文を UTF-16 の 116 単位で切る。
  `basis` に関係なく 116 で切るので、印を付けても外しても 120 を超えない。切るときはサロゲートペアを分けない。
- 落とした件数と格下げの件数を `graph_analyses` に残す（本文は残さない）。

### 6. 描画（共通の部分を含む）

- **アダプターの契約を `version: 2` に広げる**: `{version: 2, kind: "map", root}`（今の議論マップ）、
  `{version: 2, kind: "cloud", cloud: {...}}`、`{version: 2, kind: "crt", tree: {...}}`（ADR 0007）。
  `renderer.js` は同じ実行ファイルに入るので、Rust 側と同じ変更で `version: 2` に切り替え、`version: 1` は受けない（round 1 の n1）。入力の上限、失敗コード、
  例外の握り方、オフライン、ラベルをログに出さないことは ADR 0004 のまま。
- **SVG の許可リスト**: `cloud` と `causeTree`（ADR 0007）の固定の合成 fixture を svg-diagram の固定版で描き、
  出てくる要素・属性だけを足す（ADR 0004 と同じ作り方）。足したものはレビューで 1 つずつ確かめる。
- **推測の見せ方（対立解消図）**: svg-diagram の `cloud` は箱ごとの見た目を変えられない。
  v1 は、推測の要素の文頭に「〔推測〕」を付け、前提の一覧（下記）にも「推測」の列を出す。
  svg-diagram に、`cloud` の箱と前提ごとの tone（または札）を依頼し、出たらそちらに移す（議論マップの賛否の線と同じ進め方）。
- **図の下の一覧**: 前提と打ち手を表にする（矢印、前提、推測か、打ち手）。推測の前提は「会議で確かめる候補」として上から並べる。
  根拠のある要素は、選ぶとアウトラインと同じ根拠の発話を出す。
- **表示の場所**: 議論マップ（ADR 0004）と同じ部品の中に、図の種類の切り替え（議論マップ／対立解消図）を置く。
  対立解消図では、候補の一覧 → 題材（と案の組）を選ぶ →「対立解消図を作る」→ 図。作った図は題材ごとに一覧に印を付ける。
  候補が無ければ「案が対立している問いはまだありません」と出す。
- 拡大と SVG の保存は議論マップと同じ。
- **警告の扱い**（round 1 の m7）: レビューで、短い文言の合成 `cloud` を svg-diagram の MCP で描くと「text out of its box」の警告が 2 件出た。
  MCP の版が固定の v0.10.0 と同じとは限らない。タスク 3 で固定の版の fixture で確かめ、ふつうの文言で警告が出るなら、
  `maxNodeW` を広げて消えるかを試す。消えなければ svg-diagram に修正を依頼する（タスク 4）。警告の扱いは ADR 0004 のまま変えない
  （警告なら SVG を出して注意の印を付ける）。警告の種類で見分けることはしない（`renderer.ts` は警告の有無しか返さず、
  メッセージには描いた文字が入るため。round 2 の m3）。修正が出るまでは、注意の印が付いた図が多くなりうる。

### 7. 録音を止めないこと

分析は録音・セグメントの保存・文字起こし・グラフの抽出から独立したタスクで動く。録音側の `SessionStore` のロックを取らない。
LLM と描画の失敗・遅延は、分析の画面の文言にだけ出る。

### 8. 推測の要素に根拠の発話を付ける（Q4）

spike（§「計測」）で、会議で述べられた中身、とくに間接的に述べられた制約を、LLM が `inferred` にする誤りが残った。
これを人が直せるようにする。

- **関係しそうな発話**（コアの純粋関数）: 検証の段で、`inferred` の各要素（A・B・C・前提・打ち手）について、その回の入力に載せた発話から、
  要素の本文と文字の 2-gram が多く重なる順（同数は入力の順）に最大 3 件の `uid` を選び、`related` として要素に保存する。入力に無い発話は選ばない。
  日本語の分かち書きは使わない（依存を増やさないため）。あわせて入力の発話の `uid` の一覧を `input_uids` として `body_json` の最上位に保存する
  （本文は保存しない。本文はセグメントの表から `uid` で読む。round 5 の m2）。
- **画面**: 推測の要素を選ぶと、`related` の発話を並べて出し、各発話に「この発言で述べられている」を置く。並びに無いときのために
  「入力のほかの発言から選ぶ」で `input_uids` の発話をすべて出す。
- **操作は 2 つ**（round 5 の m3）:
  - **付ける**: `inferred` の要素に `uid` を 1 つ付け、`basis: stated`、`grounds: [uid]`、`by: "user"` にする（`nids` と `related` は残す）。
    1 要素に付けられる `uid` は 1 つ（付け直すには一度外す）。描画で「〔推測〕」を外す。
  - **外す**: `by: "user"` の要素だけを、付ける前の形（`basis: inferred`、`grounds` なし、`by` なし）に戻す。LLM が `stated` にしたもの、
    D・D2 は外せない（v1 の範囲を絞るため）。
- **要素の鍵**: `a`・`b`・`c`、`assumptions[i]`、`assumptions[i].injection`（`i` は保存した配列の位置）。操作は要素を足し引きも並べ替えもしないので、
  行が作り直されない限り `i` は変わらない。
- **保存**（round 5 の M1）: `graph_analyses` に `revision INTEGER NOT NULL DEFAULT 0` を足す。行を書くたび（作り直しの置き換えも、操作も）1 つ進める。
  コアの関数 `apply_analysis_edit(session, kind, subject, revision, key, op)` が、1 回の `db()` の中の `BEGIN IMMEDIATE` で
  行を読み、`revision` が画面で読んだものと同じことを確かめ、**その場で読んだ本文に**操作 1 つを当てて書き、`revision` を進める。
  画面は本文を丸ごと送らない。違えば書かずに、行が無ければ「分析が消えました」、`revision` が違えば「分析が更新されました。開き直してください」と出す。
  `uid` が `input_uids` に無い、鍵が無い、操作が当てはまらない（`stated` の要素に付ける、`by: "user"` でない要素を外す）ときは拒む。
  作り直しは §3 のとおり行を置き換えるので、人が付けた根拠は消える（作り直しのボタンの確認の文言に書く）。作り直し中に操作が来たら、
  作り直しの保存が先なら `revision` の違いで拒まれ、操作が先なら作り直しが上書きする（どちらも黙って混ざらない）。
  v0.15.0 の表にはまだアプリが書いていない（アプリは v0.14.0 を参照）ので、列を足しても移行は要らない。
- **記録**: 人が付けた根拠の数は保存しない。本文の `by: "user"` の要素を数えれば分かり、分母（作ったときの `inferred` の要素の数）も
  本文から数えられる。ログには、操作のたびに操作の種類だけを出す（本文と `uid` は出さない）。人が付けた数は (6) の率の下限の目安にしかならない
  （人が見落とした誤りは数えられない。round 5 の m5）。
- **CRT**: ADR 0007 も同じ仕組みを使う（要素は CRT のノード。鍵は ADR 0007 で決める）。

## 計測（spike）

2026-11-28 に実施（spike ブランチ `spike/conflict-cloud`、`spikes/conflict-cloud/`。マージしない）。結果は Q4 で決めた（§8）。

- 入力: 計画（下の 2 行）から変えた。流し切り＋整理の後のグラフではなく、**手で作った正解のグラフ**を使った
  （プロンプトの質をグラフの抽出の誤りから切り離すため。抽出の精度は ADR 0001 の S2 で測った）。会議は meetingram-core の
  `crates/discussion-graph/testdata/` の 6 本、S2 の 60 分の会議 `long`（候補 0）、`apps/e2e-scripted/scenarios/design`。
  候補は 29 件で、呼び出しを抑えるため各会議の先頭 4 件までの 22 件を使った。どれも合成の会議。
  `design` と `e2e-design` は入力が同じなので、独立した候補は 18 件（round 5 の n2）。
- 計画: ADR 0002 の合成会議（`apps/e2e-scripted/scenarios/`）と、ADR 0001 の S2 の合成会議で、
  案が対立する問いを持つもの。それぞれ流し切り＋整理の後のグラフを固定して使う。実在の会議は使わない。
- 各候補で 3 回ずつ、sonnet と haiku で呼ぶ。
- 測るもの: 所要時間（p50・p95）、入力の文字数、落とした件数・格下げの件数、それに Claude が 1 件ずつ読んで付ける次の判定:
  (1) A が B と C の両方に仕える目的になっているか、(2) B・C が行動ではなく要望か、(3) 前提が偽でありうる信念として書かれているか、
  (4) `stated` の要素の根拠の発話が、実際にその内容を述べているか、(5) 3 回の間で A が同じ趣旨か。
- 暫定の合格基準（提案。spike の結果で見直す）: sonnet で (1)〜(3) が 8 割以上、(4) が 9 割以上、p95 が 60 秒以内。

  （(4) の 9 割の裏返し。A は記録だけ）。

- **読み方 U**（(4) の主の値。仕様として決める）: 案を出した人が述べた利点や、反対の人の心配も、要素の中身を名指ししていれば根拠とする
  （§1「発言に根拠がある」）。読み方 S（利点の売り込みは要望の根拠にしない）では、r7 の (4) は 71.5% 以下になる。画面で根拠を開くと、
  売り込みの発言が要望の根拠として見える。これを見分けて出すかは、実際の会議で受け取られ方を見てから決める。
- **プロンプトの直し方で分かったこと**: 規則を 1 つ足すたびに、出力がその規則の言い回しに寄った（r4 の「会議で述べられていない」50/66、
  r6 の「組み合わせることはできない」53/66）。例に計測会議の言い回しを使うと答えを教えることになる（PR #52 の round 1 と round 4 の M）。
  そのため、例はすべて計測会議に無い題材（料理）にし、例の語が計測データに無いことを検索で確かめた。
- **(6) が下がらなかった理由**: B・C の誤りはほぼ直った（r7 で 3/123）。残りは前提で、とくに dd は、会議で述べられた制約を
  `stated` にしたのが 66 回中 3 回だけ。制約が「同じ欄に出す」のような画面や表の話として間接的に言われると、制約として読まない。
- **haiku**: r1 でどの基準にも届かず、(4) で根拠の合わない `stated` が 54 件あった。`graph_model` に haiku を勧めない。
- **合成の会議では確かめられず、実際の会議で見るもの**: 間接的に言われた制約を拾えるか、会議で両立できると言われているのに dd が
  両立しないと推測しないか、削減どうしの題材で dd の論理が逆にならないか、答え済みの反論を前提に押し込まないか、
  A が片方の確かめたい中身に寄らないか、抽出の誤りを含むグラフでどれだけ下がるか。

**再現手順**（`spike/conflict-cloud` ブランチ。認証済みの `claude` CLI が要る。合成の会議だけを送る）:

```sh
cd spikes/conflict-cloud
cargo test --locked                                   # fake のバックエンドで流れを確かめる
cargo run --locked -- candidates                      # 会議ごとの候補
cargo run --locked -- run --backend claude --workdir <repo の外の空のディレクトリ> --out results/rN
```

コアの版は `Cargo.toml` の `discussion-graph` の参照で選ぶ。出力は `results/rN/` の `SUMMARY.md`（時間・失敗・件数）と
`REVIEW.md`（候補ごとの出力と根拠の発話）。判定は `results/rN/JUDGE.md`。

## 影響

- **公開 API・保存形式**: コアに `graph_analyses` 表、`conflict_candidates`、対立解消図の入力の組み立て・検証の関数、分析の読み書きを足す
  （公開 API が増えるので minor）。`delete_session` が分析の行も消す。グラフの表とイベントは変えない。
  r6 で、`graph_analyses` の `revision` 列、本文の `related`・`input_uids`・`by`、人の操作の関数（§8）を足す（タスク 2b。保存形式が変わるので minor）。
- **アダプター**: `version: 2` と `kind` を足す。生成した `renderer.js` は ADR 0004 のとおり CI で再生成して差分を検査する。
- **プライバシー**: 送り先は増えない。送るのは、題材に関係するノードの本文と根拠の発話、A の手がかりとしてほかの議題の本文（最大 5 件、各 60 文字）で、会議全体の文字起こしではない。
  結果は DB にだけ保存し、ログには件数と種類だけを出す。
- **費用**: 押したときだけ 1 回（再試行で最大 2 回）。入力は 24,000 文字まで。
- **失敗したとき**: 分析の画面の文言だけ。録音とグラフの抽出は続く。
- **未確認の前提**:
  - 合成会議で、A と前提が会議の内容に沿った形で推測できる（spike で確かめた。(1)〜(4) は基準を満たし、(6) は満たさない。§「計測」）
  - 実際の会議でも同じ程度に推測でき、(6) の誤りを §8 で人が直せる *(未確認。アプリに入れてから、人が直した件数で見る)*
  - 文字の 2-gram の重なりで、間接的に述べられた制約の発話が `related` の上位 3 件に入る（round 5 のレビューの試算で r7 の (6) の誤り 52 件中 50 件。
    タスク 2b で、無作為に 3 件選んだときの期待値と並べて測り直す）
  - 確定したプロンプトは r8 の版（PR #52 のマージ時点）で、判定した r7 とは dd の規則の 1 文が違う。r8 では r7 の「両立できるかもしれない」の 13 件が
    作った制約に置き換わった。(3) と (6) への影響は判定していない *(未確認。round 5 の m4。実際の会議で見る)*

  - 推測の印が「〔推測〕」の文頭の語だけで読み分けられる *(未確認。svg-diagram の対応を待つ間の暫定)*
