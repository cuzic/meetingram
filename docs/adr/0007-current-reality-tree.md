# ADR 0007: 議論グラフと文字起こしから CRT（現状問題構造ツリー）を作る

- Status: Proposed
- 日付: 2026-11-25
- 関連: [ADR 0001 — 議論グラフ](0001-discussion-graph.md)、[ADR 0004 — svg-diagram で議論を図解する](0004-svg-discussion-map.md)、
  [ADR 0006 — 対立解消図と TOC の図の共通の仕組み](0006-conflict-cloud.md)、svg-diagram の `causeTree` 部品（v0.10.0）

## 背景

- CRT は、困りごと（UDE: undesirable effect）を上に、その原因を下にたどり、少数の根本原因（core driver）を見つける図。
  会議で「何が起きていて、なぜか」を共有し、次に確かめる原因を選ぶのに使う。
- 議論グラフ（ADR 0001）は IBIS の問い・案・賛否で、**因果を持たない**。ADR 0001 は `causes` の抽出を
  「CRT の ADR で決める」とし、ノードとエッジの種類を TEXT で足せる形にした（ADR 0001 §1）。
- 会議の中の困りごとは、グラフでは主に argument（「〜なので反対」）、issue（「なぜ〜なのか」）、position の理由に散らばる。
  原因と結果のつながりは、発言にあっても辺として抽出されていない。根本原因は口にされないことが多い。
- svg-diagram v0.10.0 の `causeTree` は、`tree: "crt"` で CRT の検査を有効にし、ノードの `role`（`ude`・`effect`・`root` など）、
  ノードごとの `tone`、リンクごとの `line`（`solid`・`dashed`・`dotted`）、AND（`from` に 2〜5 件）、
  `coreDriver`（最も多くの UDE に届く起点に印）を持つ。ノードは 30 件、リンクは 45 件まで。
- 推測の扱い、LLM の呼び方、結果の保存、描画のアダプターは ADR 0006 §1〜§3・§6 で決めた。この ADR はそれに乗る。

## 決めること / 決めないこと

- 決めること:
  - CRT の要素（困りごと・中間の事象・根本原因）と因果のつながりを、どこから、どの単位で作るか
  - LLM への入出力と検証
  - 図への写し方（推測の見せ方、AND、根本原因の印）と、作れない会議での振る舞い
- 決めないこと:
  - 推測・呼び出し・保存・アダプターの共通の仕組み（ADR 0006）
  - FRT・PRT など、ほかの思考プロセスの木
  - 根本原因を「次に聞く問い」としてヒントに出すこと（ヒントの ADR）
  - 因果を議論グラフ本体に持たせること（下の C2 で退けた。会議をまたいだ蓄積の ADR で再び検討する）

## owner の決定

ADR 0006 の Q1〜Q3 をそのまま使う（推測も出して印を付ける、ボタンを押したときだけ呼ぶ、対立解消図の後に作る）。
新しい owner の論点は無い。

## 選択肢

### どこで因果を作るか

#### C1. ボタンを押したときに 1 回の分析で作る（採用）
- 仕組み: グラフの生きたノードと根拠の発話を入力に、LLM が困りごと・事象・原因とそのつながりを一度に返す。結果は
  ADR 0006 §2 の `graph_analyses` に保存する。
- 良い点: ADR 0006 の Q2 に合う。増分・整理のプロンプト（S2 で合わせた）を変えない。因果の全体を 1 回で見るので、
  増分で見えない遠いつながり（会議の前半の原因と後半の困りごと）も結べる。
- 悪い点: 1 時間の会議ではノードと根拠が入力の上限（24,000 文字）を超える。範囲の選び方（§2）が要る。

#### C2. 議論グラフに `effect` ノードと `causes` エッジを足し、増分と整理で作る
- ADR 0001 §1 が想定した形。
- 悪い点: 会議中の毎回の呼び出しが重くなり、S2 で合わせた抽出の質が動く。根本原因は推測が多く、
  「根拠の無い操作は落とす」（ADR 0001 §2）と衝突する。ADR 0006 の Q2（押したときだけ）に反する。

#### C3. LLM を使わず、グラフから決める
- 悪い点: グラフに因果が無いので作れない。`objects_to` を因果とみなすと、反対の理由と原因を取り違える。

### 範囲

#### R1. 既定は会議全体、上限を超えるときは議題を選ぶ（採用）
- 仕組み: 入力が上限に収まれば会議全体。収まらなければ、利用者が議題を 1〜3 個選ぶ（ADR 0004 の「範囲を選び直す」と同じ考え）。
- 良い点: 短い会議では選ばずに済む。長い会議でも、自動で一部を捨てない（ADR 0004 と同じ方針）。

#### R2. いつも議題を 1 つ選ぶ
- 悪い点: CRT の価値は議題をまたいだ共通の原因（core driver）を見つけることにあり、1 議題では見えにくい。

## 決定

**C1・R1 を採る。**

### 1. 題材の鍵

ADR 0006 §2 の `subject` は、会議全体なら `"all"`、議題か細かな問いを選んだら `"issues:{nid},{nid}"`（nid は昇順）。

### 2. 入力

- 対象のノード: 範囲の中の生きているノード（`merged`・`rejected` でない）。議題を選んだときは、その議題と `sub_issue_of` の子孫、
  それらに `responds_to`・`resolves` で付くノード、それらの issue と decision に `assigns` で付く action、
  position と argument に `supports`・`objects_to` で付く argument を、たどれなくなるまで（round 1 の m5）。
  エッジは生きているもの（`review = rejected` でなく、両端が対象）だけ。
- 各ノード: `nid`、種類、本文、状態。エッジ: `src`、`dst`、種類。
- 根拠の発話: ノードごとに先頭 1 件を 200 文字まで（`uid`、話者ラベル、本文）。
- 上限（24,000 文字）を超えるときは、根拠の発話を 1 件 100 文字に切り詰める。根拠の発話は外さない
  （ADR 0006 §1 の `stated` は発話を根拠に要し、外すと UDE がすべて推測に格下げされて図にならないため。round 1 の M3）。
  それでも超えるなら LLM を呼ばず、範囲を選ぶよう画面に出す（R1）。
- 範囲の選び方（round 1 の m5）: 議題を 1〜3 個選ぶ。議題 1 つでも超えるときは、その議題の細かな問い（`sub_issue_of` の子）を 1〜3 個選べる。
  細かな問い 1 つでも超えるなら「この範囲は図にするには大きすぎます」と出す。
- 会議全体の文字起こしは渡さない（送る量をグラフと根拠に絞る。ADR 0006 §4 と同じ）。

### 3. 出力と検証

```json
{"entities": [
   {"id": "e1", "text": "…", "role": "ude", "basis": "stated", "grounds": ["u31"], "nids": ["n12"]},
   {"id": "e2", "text": "…", "role": "effect", "basis": "inferred", "nids": ["n4"]}
 ],
 "links": [
   {"from": "e2", "to": "e1", "basis": "stated", "grounds": ["u30"]},
   {"from": ["e3", "e4"], "to": "e2", "basis": "inferred"}
 ]}
```

- 書き方の規則（system）: 事象は現在の事実の文で書く（「〜していない」「〜が多い」）。人を原因にしない。
  UDE は、会議で困りごととして語られたものだけにし、`stated` にする（推測の困りごとを作らない）。
  つながりは「原因が成り立てば結果が起きる」と読めるものだけ。どちらか一方では足りないときは AND にする。
- `role` は LLM が `ude` か `effect` を付ける。**根本原因はアプリが決める**: 入ってくるつながりが無く、出ていくつながりがある `effect` を `root` として描く
  （LLM の申告を使わない）。UDE は入ってくるつながりが無くても `root` にせず `ude` のまま描き、「原因が見つからない困りごと」として表にも出す（round 1 の m4）。
- 検証（コアの純粋関数。不正な部分だけを落とす）。**下の表の順に、表の上の行から 1 回ずつ適用する**（round 1 の M4）:

| 順 | 対象 | 落とす・直す条件 |
| --- | --- | --- |
| 1 | 全体 | JSON として読めない → 失敗 |
| 2 | 事象 | `id` が重複（2 件目以降）・空、本文が空 → 落とす。120 単位（UTF-16）を超える → 切る。`role` が `ude`・`effect` 以外 → `effect` |
| 3 | 根拠 | 事象とつながりの両方に、ADR 0006 §1 と同じ規則（入力に無い `uid`・`nid` を落とし、`grounds` が残らない `stated` は `inferred` に格下げ） |
| 4 | UDE | `ude` で `basis` が `inferred`（3 の格下げを含む）→ `effect` に直す |
| 5 | つながり | 端点が存在しない id（出力に無い、または 2 で落ちた事象）、自己ループ、AND が 2〜5 件の外、同じ組（`from` の集合と `to`）の重複 → 落とす |
| 6 | 閉路 | 出てきた順に 1 本ずつ足し、足すと閉路ができるものを落とす（AND は `from` の各事象から `to` への辺として数える。v1 は循環を描かない） |
| 7 | 孤立 | どのつながりにも乗らない事象を外す。UDE は図から外すが、「原因が見つからない困りごと」として表に残す |
| 8 | 件数 | 事象が 30 件を超える → UDE を先に、次に残ったつながりの端に現れる回数の多い順（同数は出てきた順）で 30 件を残し、外した事象に触れるつながりを落とす。その後もう一度 7 を適用する。つながりが 45 本を超える → 出てきた順で 46 本目以降を落とし、もう一度 7 を適用する |
| 9 | 根本原因 | 上の「根本原因はアプリが決める」で `root` を付ける |
| 10 | 空 | 図に残る UDE が 1 件も無い、またはつながりが 1 本も無い → 「作れなかった」（§5） |

- 落とした件数と格下げの件数を `graph_analyses` に残す。

### 4. 図への写し方

- `causeTree`、`tree: "crt"`、`dir: "up"`（原因が下）、`coreDriver: true`、`coreDriverLabel` は「UDE {n}/{total} に届く」。
- 推測の見せ方: 推測の事象は `tone: "muted"`、推測のつながりは `line: "dashed"`。発言の事象とつながりは既定の見た目。
  UDE は svg-diagram の `ude` の見た目に従う。凡例に「薄い箱・破線 = 推測」を書く（ADR 0006 §1）。
- svg-diagram の CRT の検査が警告を返したら、図は出して注意の印を付ける（ADR 0004 の警告の扱いと同じ）。エラーなら `render_failed`。
- 図の下の一覧: 根本原因（core driver を先頭に、届く UDE の数の順）と、原因の見つからない UDE。推測の根本原因は「会議で確かめる候補」として示す。
  根拠のある要素は、選ぶとアウトラインと同じ根拠の発話を出す。
- 表示の場所は ADR 0006 §6 の図の種類の切り替えに「CRT」を足す。範囲（会議全体／選んだ議題）を図の見出しに書く。

### 5. 作れない会議

困りごとを話していない会議（決めごとだけの会議など）では UDE が出ない。検証の後に UDE かつながりが無ければ、
保存せずに「この会議からは困りごとの因果をまとめられませんでした」と出す。この場合も費用はかかるので、
ボタンの説明に「困りごとや原因を話した会議で使う」と書く。

## 計測（spike）

未実施。ADR 0006 の spike の後に、同じやり方で行い、結果をこの ADR に追記する。

- 入力: 困りごとと原因を話す合成会議を 3 本新しく作る（実在の会議は使わない）。各会議に、正解の UDE（3〜5 件）と、
  会議の中で口にされる原因のつながり、口にされない根本原因を 1 つずつ置く。ADR 0001 の S2 の合成会議 6 本も、作れない会議の確認に使う。
- 各会議で 3 回ずつ、sonnet と haiku。
- 測るもの: 所要時間（p50・p95）、入力の文字数、落とした件数・格下げの件数、それに Claude が付ける判定:
  (1) 正解の UDE の再現率、(2) 推測でない UDE の割合（`stated` の根拠が実際に困りごとを述べているか）、
  (3) 口にされたつながりの再現率、(4) つながりの向きの誤り（結果 → 原因）の件数、(5) 正解の根本原因が根本原因か core driver に出るか、
  (6) 困りごとを話していない会議で、UDE を作らずに「作れなかった」になるか。
- 暫定の合格基準（提案）: sonnet で (1) 8 割以上、(2) 9 割以上、(3) 6 割以上、(4) 会議ごとに 1 件以下、(6) 6 本中 5 本以上。p95 が 90 秒以内。

## 影響

- **公開 API・保存形式**: コアに CRT の入力の組み立て・検証の関数を足す。保存は ADR 0006 の `graph_analyses`（`kind = 'crt'`）で、表は増えない。
  ADR 0001 §1 が想定した `effect` / `causes` の種類は使わない（C2 で退けた）。グラフの表とイベントは変えない。
- **アダプター**: ADR 0006 §6 の `kind: "crt"` を実装する。許可リストに `causeTree` の fixture の分を足す。
- **プライバシー・費用・失敗したとき**: ADR 0006 と同じ。送るのはグラフのノードと根拠の発話（先頭 1 件）で、会議全体の文字起こしではない。
- **未確認の前提**:
  - グラフのノードの本文と根拠の先頭 1 件だけで、口にされた因果を拾える *(未確認。spike で測る。足りなければ根拠を増やす)*
  - 1 時間の会議の会議全体が入力の上限に収まる割合 *(未確認。spike で入力の文字数を記録する)*
  - svg-diagram の CRT の検査が、v1 の検証を通った木で警告を出さない *(未確認)*
