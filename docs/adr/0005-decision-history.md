# ADR 0005: 会議内で決定と宿題の変更を追う

- 状態　Proposed
- 日付　2026-11-24
- 関連　[ADR 0001 議論グラフ](0001-discussion-graph.md)、[ADR 0002 台本付き E2E](0002-e2e-scripted-backends.md)

## 背景

現行のアウトラインは、一つの問いの下に決定と宿題を並べ、選んだノードの根拠を表示する。たとえば前半で「火曜にリリース」と合意し、終盤で「火曜は検証、リリースは木曜」と訂正した場合、両方の決定が並んでも、後者が前者を置き換えたかは分からない。現行の `set_status(retracted)` は案と理由に限られ、決定や宿題の変更を表せない。要約と議論グラフは別々に生成されるため、同じ会議でも古い決定の扱いが食い違い得る。

会議の途中で顧客や対象成果物が切り替わることもある。「同じ議題に見える」「後の発話だった」という理由だけで決定や宿題を結び付けると、別の対象の決定を誤って撤回できてしまう。

## 選択肢

- **発話順に並べ、最後を現行とする。** 既存データで出せるが、並行した決定、伝聞、反対意見、再文字起こしによる順序のずれで誤る。
- **追加の根拠とともに変更を記録する。** 人が対象と根拠を選び、確認して確定する。将来は AI が候補を提案できる。どの決定を変えたかと、変更を裏付ける発話が残る。レビューと保存形式の拡張が要る。
- **会議後の結果だけを再抽出する。** 実装は比較的独立するが、変更前の判断を失いやすく、要約やグラフとの整合を別途取る必要がある。

## 決定案

### 同じ会議での、明示的な変更を扱う

初版は決定の撤回・置換と、宿題の撤回・置換を扱う。担当交代や期限変更は宿題の置換で表す。問いの再開は、決定が撤回されても他の決定で解決済みの場合があるため、別の操作として後続で検討する。新しい読み書きは現在の `session_id` に限定する。別セッションの発話・ノードを候補検索、照合、LLM 入力に使う経路を設けない。

置換では変更前後の同種ノードを参照し、撤回では変更前のノードを参照する。両方に、変更そのものを示す発話を付ける。変更前後の発話と変更の発話は重複してよい。置換候補を示す条件は、発話が同じ対象の以前の判断に対する訂正や差し替えを示していること。議題の所属、表現の類似、発話順は候補を絞る補助情報に使える。明示的な対象を特定できないときは、リンクを作らず、当該ノードの根拠を通常どおり表示する。

初版の候補は、会議後の履歴で人が作る。置換先と変更発話は現在の会議から選び、確認画面で前後の根拠と変更発話を見比べる。承認には「変更前後が同じ顧客・成果物などの対象を指す」ことの明示確認を要する。撤回では、変更発話が元の判断と同じ対象を指すことを確認する。同じ議題への所属も対象の同一性を保証しない。別の対象だと分かる場合や根拠から判断できない場合は、承認できず、候補のままにするか却下する。この判断は人が行うため、データ上の検証だけで対象間の誤認を防げる保証はない。

### 保存・確認・読み取り

変更候補を本文を持たない独立したレコードにし、対象ノード、置換先、変更種別、根拠 UID、レビュー状態を保存する。本文はセッション内の既存ノードと発話から読む。候補とそのレビューは既存グラフの書き込みトランザクションで保存し、成功時にグラフのリビジョンを進める。

同一セッションの生存ノード、同種、実在する根拠、自己参照の禁止を検証する。候補の根拠は作成後に書き換えない。同じ端点・種別・根拠の組は既存候補を返す。却下・取消後に再検討するときは人が元の候補を開き直す。根拠が異なる新情報は別候補にできる。

候補の作成と状態変更は `source = review` のパッチに ID と操作だけを残す。書き込みは既存のレビューと同様に、アプリ内の作り直しカウンターと DB のリビジョンの両方を照合する。カウンターは `GraphStatus::graph_generation` のことで、ADR 0001 で見送った永続グラフ世代は追加しない。リビジョンが作り直し後に同じ値へ戻っても、古い画面からの操作は拒否する。グラフを作り直す場合は候補・レビューも同じ削除トランザクションに含め、確認画面に明記する。

| 現在の候補状態 | 操作と次の状態 |
| --- | --- |
| 確認待ち | 承認、または却下 |
| 承認済み | 取消。置換先を起点に承認済みの変更がある場合は、下流から先に取り消す。 |
| 却下・取消済み | 人が開き直して確認待ちに戻す。 |

承認時に参照と対象の確認を再検証し、一つのノードから複数の承認済み変更が出ることと、置換が循環することを拒否する。確認待ち・承認済みの候補の端点を、既存の `merge` の from・into のどちらにも使えないようにし、端点のノードを却下する前に候補を却下または取り消す。候補作成時点で既に統合済みの端点は拒否する。統合前のノードを取り戻せない既存セッションでは、人が別々の判断を復元できる仕組みを後続で検討する。

現在表示は生存ノードと候補の状態から導く。`graph_nodes.status` は変更しない。承認済みの置換・撤回の起点は現在の一覧から外し、履歴に残す。A→B→C を承認すると C が残り、B→C を取り消すと B が戻る。A→B と B の撤回を承認した場合、この系列の現行項目はなく、A は復活しない。確認待ちの候補がある項目は、確認済みの現在一覧と区別して「確認待ち」に置き、複数候補があればすべて表示する。ただし、すでに承認済みの変更がある起点の競合候補は、その承認を取り消すまで現在表示に影響しない。却下・取消済みの候補は履歴だけに出す。変更記録のない項目は従来どおり表示し、表示上「承認済み」とは扱わない。

### 表示

ライブと履歴のアウトラインから変更前・変更後・変更を示す発話を直接開けるようにする。履歴画面で候補を承認・却下し、承認を取り消せる。時刻がある発話には時刻を出す。時刻がない発話は取り込み順で表示し、順序から新旧を推定しない。

要約画面には同じグラフの読み取り結果を使う「決定・宿題の変更」を表示する。変更候補がある会議では根拠付きの変更を先に出し、生成要約本文は初期状態で折りたたむ。開く操作に生成日時と「変更確認の結果は要約本文に反映されません」を表示する。既存要約の再生成や書き換えは不要で、グラフのない旧セッションでは従来どおり要約本文を表示する。

## 受け入れ条件と実装順

| 順 | repo | 変更 | 受け入れ条件 |
| --- | --- | --- | --- |
| 1 | core | 変更候補、根拠、レビュー、現在の読み取りを追加 | 合成データで決定の置換、担当交代、撤回、取消、再承認を確認する。A→B→C の取消順、B の撤回で A が戻らないこと、競合候補の承認拒否、端点の統合拒否、別セッション参照と循環の拒否をテストする。 |
| 2 | app | アウトライン・履歴で変更と根拠を表示し、候補作成とレビューを追加 | Windows E2E で決定が覆る前後の発話を開いて承認できる。別顧客の類似した決定を誤って選ぶケースで、根拠を比較し、同一対象の確認なしでは承認されず、却下後も現在一覧が変化しない。作り直しや別操作の前に開いたレビューは拒否する。 |
| 3 | app | 要約画面に同じ読み取り結果を表示 | 一回の承認・取消が両画面に反映される。変更前の要約は初期状態で閉じており、開けば生成日時と注意文が読める。グラフのない旧セッションでは従来の要約が読める。 |

初版は手動で候補を作るため、会議本文の新しい送信先や追加の LLM 呼び出しを必要としない。将来の AI 提案は別の設計判断とし、別顧客への誤リンクや、明示的な撤回・置換の取りこぼしを測る合成データと基準を定めてから検討する。発話本文と候補本文はログに出さない。
