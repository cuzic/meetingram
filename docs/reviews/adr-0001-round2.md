## Findings

### N1（Major）: 2 本目の接続で、録音後の音声保存が `SQLITE_BUSY` で失敗しうる。流し切りはその窓で始まる
- 根拠:
  - Windows の録音は、音声フレームをメモリに溜め、`join!` の後に `run_pipeline` でまとめて保存する（core `crates/app-service/src/windows_session.rs:123-141`）。
    各セグメントは `commit_segment(...)?`（`pipeline.rs:139`）→ `store.register_segment(&segment)?`（`segment_writer.rs:108`）で保存する。
    `register_segment` はトランザクションで書く（`store.rs:378`）。ここが失敗すると `?` で `run_pipeline` が抜け、残りのセグメントは保存されない（メモリ上のフレームを失う）。
  - 今は同じプロセスの書き手が全員 1 つの `Mutex<Connection>` に並ぶので、プロセス内で `SQLITE_BUSY` は起きない。
    P はプロセス内に 2 人目の書き手を作るので、グラフ側が書きのロックを 5 秒（`busy_timeout`、`schema.rs:163`）より長く持つと、録音側の書き込みが `SQLITE_BUSY` で失敗する。
  - `UtteranceEnded(SessionEnd)` は `run_live_transcription` の中、つまり `run_pipeline` の**前**に publish される（`live_transcription.rs:902-914`）。
    §3 の流し切りは「`stopped` か `SessionEnd` の後」に始まるので、取り込みとパッチの書き込みが、ちょうど音声の保存と重なる。
    一方 `session.{sid}.stopped` は capture のタスク（`run_pipeline` を含む）が終わった後に出る（`apps/desktop/src/recording.rs:170-179`）。
  - ADR は「書きは短いトランザクションだけ」と書くが、長さの上限も、`BEGIN IMMEDIATE`（遅延トランザクションで読んでから書くと、WAL では busy handler を通らずに `SQLITE_BUSY` が返る）も決めていない。
- 修正案:
  - 流し切りの開始を `session.{sid}.stopped` だけにする（`SessionEnd` では始めない）。
  - §7 に次を書く。グラフ側の書き込みは `BEGIN IMMEDIATE` で、1 トランザクションに 1 パッチ（または取り込み 1 回）だけ。作り直しの削除もセッション単位の短いトランザクション 1 つ。
  - タスク 3 に「グラフ側がトランザクションを開いている間に `SessionStore::register_segment` が成功する（待ってから通る）テスト」を足す。

### N2（Major）: 流し切りに終わる条件が無く、先頭の 1 件で詰まりうる
- 根拠:
  - §3 の 2 は「未抽出の発話が無くなるまで増分の抽出を続ける（会議中に止めていても行う）」。
    §2 は、読めない応答・LLM の失敗では「発話は未抽出のまま残る」。§7 の「3 回失敗で停止」は会議中だけ。
    そのため、キーが無い・ネットワークが無い・プロバイダが落ちている・CLI が見つからないと、流し切りは同じ発話で LLM を呼び続けて終わらない。
  - 新しい発話は「`uid` 順に上限の文字数まで」入れる。文脈（「open の issue 全部」）は会議の長さとともに増え、上限が無い。
    文脈だけで 24,000 文字に近づく場合や、1 件で残りの枠を超える発話がある場合は、先頭の発話が入らず、どの回も進まない。
    `persist_pending_interim` の行や時刻の無い STT の長い確定行で起こりうる。
  - Q5 で既定が有効になったので、キーを設定していない人の会議でもこれが起きる（n4）。
- 修正案:
  - 流し切りにも連続失敗の上限（例: 3 回）を置き、超えたら止めて UI に「未抽出 N 件」と出す（作り直しのボタンで再開）。
  - 文脈に文字数の枠（例: 上限の 1/3）を設け、open の issue は新しい順に入れる。
  - 1 件で枠を超える発話は、切り詰めて入れるか、抽出せずに「抽出済み・ops なし」にして先へ進む。
  - タスク 5 に「LLM が常に失敗しても流し切りが有限回で終わる」「24,000 文字を超える 1 件の発話でも後続が抽出される」テストを足す。

### N3（Major）: 作り直しと会議後の処理が、同じセッションで同時に走りうる
- 根拠: 作り直しは履歴画面のボタンから「グラフの表の行を消して流し切り→整理」をする（§3）。
  会議の後の流し切り（長い会議では数分〜十数分の LLM 呼び出し）は `graph_consumer` のタスクで走る。
  ADR には、セッションごとに 1 つしか走らせない約束が無い。並ぶと次の問題が起きる。
  - 削除の後に、走っていた側が古い `rev` や `nid` でパッチを書く。
  - `uid` の連番と `rev` が両方から振られて、主キーが衝突するか、消えたノードを指すエッジが残る。
  - 「作り直し」を 2 回押した場合も同じ。
  - 録音中のセッションも履歴で選べるので（`ui.rs:552-562`）、録音中に作り直しを押せる。
- 修正案: §3 と §7 に次を書く。
  - `discussion-graph`（またはアプリ）が、セッションごとの実行者を 1 つに限る（`HashMap<SessionId, JoinHandle>` か、DB の `graph_runs` 行で排他）。
  - 作り直しは、走っているものを止めて（または終わるのを待って）から消す。録音中のセッションでは作り直しを出さない。
  - `rev` と `uid` は、トランザクションの中で `MAX(...) + 1` を取って振る。
  - タスク 5 にこの排他のテストを足す。

### n1（Minor）: 検証の規則の表に残る穴と矛盾
- 根拠（§2 の表）:
  - `merge` の付け替えで `from`→`into` のエッジが自己ループになる場合を落とすと書いていない。
  - 付け替えでは人の判断済み（`approved` / `rejected`）の**エッジ**の端点も変わり、「人の判断はノードもエッジも守る」と食い違う。
  - 「`into` は常に `merged` でないので連鎖は起きない」は、同じパッチの中では成り立たない。`merge A→B` の後に `merge B→C` が来ると `A.merged_into = B`（`merged`）が残る。
    検証を「それまでの操作を適用した状態」に対して行うのかも書いていない。
  - `set_status` で、対象が `merged`／`rejected` のノードの場合が落とす条件に無い。`act` の値の検査も無い。
- 修正案: 付け替えで生じる自己ループと重複は捨てる。人の判断済みのエッジを持つノードは `from` にできない。
  `merge` の適用で、`merged_into = from` のノードも `into` に向け直す。検証は逐次に適用した状態に対して行う。
  `set_status` は `merged`／`rejected` を落とし、未知の `act` も落とす。それぞれ表に 1 行ずつ足す。

### n2（Minor）: 24,000 文字の根拠と、整理の分け方がまだ埋まらない場合
- 根拠: Windows の上限は UTF-16 の 32,767 単位で、プログラムのパスと他の引数を含む。
  `"` などの引用符のエスケープで文字数が増える。npm で入れた CLI が `.cmd` のシムだと、cmd.exe の 8,191 文字の上限と、Rust の batch 引数の制限が先に当たる。
  整理は「issue ごとのまとまり」に分けるが、1 つの issue の部分グラフが 1 回で 24,000 文字を超える場合が無い（大きい議題 1 つの会議）。
- 修正案: S1 で、Windows の実機で両 CLI の実際の上限を測る項目を足す。1 つの issue が上限を超えたら、根拠の発話の本文を切り詰める（または根拠の数を絞る）と §3 に書く。

### n3（Minor）: 会議の後の再文字起こしの行は、合図が無いので取り込まれない
- 根拠: §1 は「後からの再文字起こし（`is_retranscribed = 1`）も同じ経路で 1 回ずつ取り込まれる」とする。
  しかし再文字起こしは会議の後に履歴画面から手で行い（`apps/desktop/src/gap_retranscription.rs`）、その時点で `graph_consumer` は終わっている。イベントも出ない。
  取り込まれるのは作り直しを押したときだけで、その場合は承認・却下も消える。
  また、`row_id` の順に並べるので、会議の前半の穴を埋めた発話がグラフでは最後に並び、「直前の 3 発話」も時間の上で隣ではない。
- 修正案: 再文字起こしが終わったら、そのセッションの増分の取り込みと抽出（承認・却下は消さない）を 1 回走らせると §3 に書く。少なくとも UI に「未取り込みの発話 N 件」を出す。
  並びの例外（再文字起こしの行だけ時刻で前後を決める、または参照用の 3 発話を付けない）も決める。

### n4（Minor）: 既定で有効（Q5）にした結果、本文の扱いが足りない
- 根拠: `hint_enabled` を opt-in にした理由は「設定していない環境で、毎回失敗してログを出し続ける」ことだった（`apps/desktop/src/app_settings.rs:80-86`）。
  グラフも、要約のプロバイダを選んでいないと Claude の API が既定になり（`summary_consumer.rs:235`）、キーが無ければ毎会議で 3 回失敗し、「グラフの更新を止めた」が出る（流し切りは N2）。
  また、§5 は Windows だけとするが、タスク 5 に「macOS では consumer を起動しない」が無い。
- 修正案: 録音の開始時に、要約のバックエンドが組み立てられない（キーが無い・CLI が無い）ならグラフの consumer を起動せず、設定画面に理由を出すと §3 に書く。
  タスク 5 に「macOS では起動しない」を足す。

### n5（Minor）: 依存の向きは決まったが、使う API がコアで公開されていない
- 根拠: `open_with_pragmas` は `session_store` の private な `mod schema` にあり（`crates/session-store/src/lib.rs:7`）、外から呼べない。
  `transcript-event` は `TrackKind` を再公開していない（`use recorder_domain::{SessionId, TrackKind}`、`lib.rs:24`）。
  グラフの表には外部キーが無いので、「表の作成の順序のため」に session-store へ依存する理由は弱い。ただし `transcript_segments` を直接読む結び付きはある。
  発話の話者ラベル（「自分 (話者2)」）を作る関数も、`app-service`・アプリ・`rhai-engine` に写しがあり、公開されたものは無い（`live_transcription.rs:98-103` の注記）。
- 修正案: 「影響」の公開 API に次を足す。
  - session-store が `open_with_pragmas`（または `open_secondary_connection`）を公開する。
  - `TrackKind` と `SessionId` は `recorder-domain` から取る。
  - 話者ラベルの関数を `transcript-event` か `recorder-domain` に 1 つ置く。
  - これらをタスク 3 のスコープに入れる。

## 判定
converged: no（Blocker 0 / Major 3 / Minor 5 / nit 0）
