## Findings

### m1（Minor）: 行を消して作り直すと `revision` が 0 に戻り、古い画面の操作が別の分析に当たりうる
- 根拠: §8「`revision INTEGER NOT NULL DEFAULT 0` … 行を書くたび 1 つ進める」。作り直しの置き換え（upsert）なら進むが、
  `delete_analysis`（利用者の削除）や `delete_session`（グラフの作り直し）で行を消した後に同じ鍵で作り直すと、新しい行は 0 から始まる。
  一度も操作していない古い分析（`revision` 0）を開いたままの画面から操作が来ると、照合は通る。新しい行の `input_uids` に同じ uid があれば
  （uid はセグメントの識別子で、グラフを作り直しても変わらない）、新しい分析の要素に当たる。r5 までの照合にあった `created_at` は外れた。
  アプリは 1 窓で、保存の後に画面は行を読み直すので起きにくいが、§8 の「どちらも黙って混ざらない」は、この場合には成り立たない。
- 修正案: 照合を `(created_at, revision)` の組にする（`created_at` はミリ秒で、作り直しには LLM の呼び出しが挟まるので重ならない）。
  2b のテストに「消して作り直した行に、古い `revision` 0 の操作が当たらない」を足す。

### m2（Minor）: §8 を CRT にも当てると書いたが、共通の節の一覧と ADR 0007 が追従していない
- 根拠: §8 の末尾「CRT: ADR 0007 も同じ仕組みを使う（要素は CRT のノード。鍵は ADR 0007 で決める）」。
  一方で §「決定」の冒頭（100 行）は、共通の仕組みを「§1〜§3 と §6」とし、§8 を入れていない。ADR 0007（Accepted）も「ADR 0006 §1〜§3・§6 に乗る」（0007:19）のままで、
  0007 のタスク 2・3 に §8 の関数と画面が無い。CRT にはつながり（エッジ）にも `basis` があり、鍵をノードだけにするのかも決まっていない。
- 修正案: 100 行の共通の一覧に §8 を足し、ADR 0007 に「§8 はノードとつながりのどちらに当てるか、鍵の形は 0007 の改訂で決める。それまで CRT には §8 を出さない」と 1 行足す。
  または 0006 の §8 の CRT の行を「v1 は対立解消図だけ。CRT は ADR 0007 の改訂で決める」にする。

### n1（nit）: 無作為の期待値の式「3 / 入力の発話の数」は、正しい uid が複数あると低すぎる
- 根拠: 2b は「どれかが入れば当たり」にしたが、期待値は 1 件ごとに 3/n で足す。`m2/g3` の u119/u120、`m2/g2` の u12/u81 のように正しい uid が k 件ある誤りでは、
  無作為の当たりの確率は 1 − C(n−k, 3)/C(n, 3) で、3/n より大きい。式のずれは、2-gram が当たりやすく見える向きに働く。
  round 5 の試算（期待値 31.6）は、この式で出したもの。「未確認の前提」の「52 件中 50 件」も、無作為で約 32 件、入力が 3 件の候補（i-notice）は必ず当たる、と添えないと高く読める。
- 修正案: 2b の式を 1 − C(n−k, 3)/C(n, 3) にし、「未確認の前提」に無作為の期待値（約 32 件）を併記する。
