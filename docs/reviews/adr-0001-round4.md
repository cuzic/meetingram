## Findings

### M1（Major）: タイムアウトで「子プロセスを止める」と、孫の CLI 本体が残る（Windows の `.cmd` と npm 版の codex）
- 根拠:
  - §2 で `.cmd` のシムを起動するようにした。Windows では Rust が `cmd.exe /c claude.cmd` を起動し、cmd.exe が node を、node が本体を起動する。
    npm 版の codex は Linux や macOS でも、`bin/codex.js` が `spawn(binaryPath, ...)` で native の本体を起動する（`@openai/codex` 0.167.0 の `codex.js:247`。
    中継できるのは SIGINT などで、SIGKILL は中継されない）。
  - 今のコードの `kill_on_drop(true)`（`cli_backend.rs` の `run_claude` / `run_codex`）や `Child::kill` が止めるのは直接の子だけ。
    §7 の「上限を超えたら子プロセスを止めて捨てる」をこの方法で実装すると、本体が動き続ける。文字起こしの送信とトークンの消費が続き、
    §3 の「同時に動く呼び出しは 1 つまで」も実際には破れる。Windows では孫が作業ディレクトリ（`-C` の一時ディレクトリ）をつかんだままなので、
    「失敗・タイムアウトでも消す」（§2）の削除が失敗する。
  - タスク 4 の受け入れ条件に、プロセスツリーを止めるテストが無い。
- 修正案: §7 に「プロセスツリーごと止める」と書く（Windows は `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` の Job Object に入れて起動する。Unix はプロセスグループを作って `killpg` する）。
  タスク 4 に、孫を起動して眠り続けるダミーの CLI（Windows では `.cmd`）がタイムアウトしたら、孫が消え、一時ディレクトリも消えるテストを足す。

### M2（Major）: codex の呼び方が「PR #9 の lean と同じ設定」ではない。シェル、画像、Web 検索のツールが有効なまま
- 根拠:
  - §2 の codex の行には `-c features.shell_tool=false`、`-c features.view_image=false`、`-c web_search="disabled"` が無い。
    PR #9 の lean にはこの 3 つが入っている（`spikes/s1-discussion-graph/src/backend.rs` の `CliMode::Lean`）。
    `--ignore-user-config` で利用者の設定も読まないので、codex の既定のツールがそのまま有効になる。
    `-s read-only` でもシェルはディスク全体を読める。Web 検索は、発話の中身を検索語に入れて外に出しうる。
    文字起こしには会議の参加者の発言が入るので、プロンプトインジェクションの入口になる。claude 側は `--tools ""` で全部切っているのに、codex 側だけが開いている。
  - 応答の受け取り方も書いていない。今のコードと PR #9 は `-o <file>` で最後のメッセージをファイルに受け、PR #9 は `--json` でトークン数を取る。
    §2 はどちらも外している。0.167.0 では、`-o` が無ければ最後のメッセージは stdout に出た（手元で確認）。
    一方、stderr には user の全文（文字起こし）と応答がそのまま出る（手元の probe で確認）。
- 修正案: codex の行を PR #9 の lean のフラグ全部にそろえる（3 つの無効化を足す）。応答は `-o` で受けるか stdout で受けるかを決めて書く。
  `-o` で受けるなら、その出力ファイルも一時ファイルとして、消す対象に入れる。タスク 4 に、組み立てた引数の列を固定するテストを足す（PR #9 の `cli_arguments_match_backend_and_mode` と同じ形）。

### M3（Major）: 今の要約を lean のフラグに移すと、いま動いている CLI の要約が壊れる。代わりの経路も受け入れ条件も無い
- 根拠:
  - `--setting-sources ""` は claude の user / project / local の settings を読まない。settings の `env`（`ANTHROPIC_BASE_URL`、プロキシ、Bedrock / Vertex の切り替え）や
    `apiKeyHelper` で認証やモデルの別名を設定している人は、要約が `non_zero_exit` になる。
  - `--ignore-user-config` は codex の `config.toml` を読まない。`model_provider`（Azure など）や既定のモデル、reasoning effort の設定も無視される。
    今のコードは「モデルが空なら CLI に設定済みの既定を使う」（`summarize_via_cli` のコメント）。この前提も成り立たなくなる。
    手元では、`--ignore-user-config` を付けると codex の組み込みの既定モデルが選ばれた。
  - 古い版には `--tools`、`--system-prompt-file`、`--ignore-user-config` が無い。「影響」は「フラグが通らないときは `non_zero_exit` になる」とだけ書き、そのまま受け入れている。
    v1 のグラフだけなら新機能の制約で済む。しかし既存の要約まで巻き込むと、更新した人の要約が黙って止まる。
- 修正案: 次のどれかを決めて §2 と「影響」に書く。
  - フラグが拒否されたら、今の呼び方（本文は標準入力に移したもの）で 1 回やり直す。
  - 起動時に `--help` か版を見て、lean にするかを決める。
  - 要約は今のフラグのまま標準入力にだけ移し、lean にするのはグラフだけにする。

  あわせて、両 CLI の最小の版を書く。タスク 4 に「lean のフラグを拒否するダミーの CLI でも要約が返る」テスト（またはエラーの種類と UI の表示のテスト）を足す。

### M4（Major）: タスク 4b の合格の目安は、整理を強める前の結果ですでに満たされている。1 時間の会議で必ず通る分割の経路も測らない
- 根拠:
  - 目安は「整理の後の適合率（sonnet、A の正解）が 0.6 以上」。ところが A の sonnet は、強める前の整理でもう 0.79 / 0.60 / 0.62 ある（`spike/discussion-graph/README.md`）。
    S2 で整理のプロンプトが効かなくても、目安は通る。
  - 「ノードが正解の 2〜4 倍」は、整理の無い B の結果だけ。B の正解は 39〜42 ノードで、予測は 89〜170。
    A の整理の後の生きているノードは 48〜71 で、正解の 33〜46 の 1.2〜2.1 倍（`results/*.json` から数えた）。強化の動機になった B の正解は、目安から外れている。
  - 整理の入力が 1 万〜1.2 万文字なのは、11〜16 分の会議でのこと。1 時間の会議ではその 4〜5 倍になり、上限の 24,000 文字を超える。
    だから実際の会議では、§3 の「issue ごとに分けて呼ぶ」経路を毎回通る。§2 の「どちらも余裕がある」は整理には当たらず、S2 もこの分割の経路を一度も通らない。
- 修正案: 4b の目安を、強める前との差にする。たとえば「A と B の両方の正解で、整理の後の重複の数が強める前より X% 減り、適合率が Y 以上」。
  B の 3 本を同じ形式に直すのを、タスク 2 の「できれば」から 4b の必須に上げる。
  合成会議をつないだ約 60 分の入力を 1 本足し、分割の経路で issue をまたぐ重複が統合されることと、所要時間（120 秒 × 呼び出しの数）を測る。§2 の「余裕がある」は増分にだけ言う。

### m1（Minor）: §「計測」の数値のずれ
- 根拠:
  - sonnet の lean の入力は 2,814 / 2,974 / 2,887 トークン/回なので「2.8〜3.0k」（ADR は 2.8〜2.9k）。
  - A の m1 は 690,778 ms で約 11.5 分（ADR は「約 13 分」）。
  - 「整理の `merge` は 1 会議で 4〜19 回」は、整理の 1 回の操作の数（`n_ops`。種類を問わない。ctxall の 3 本は 2）。
    最終のグラフの `merged` は 0〜16 で、0 の実行が 3 本ある。
  - B の「検証で落ちた操作」は `add_edge` の 0〜3.4% のほかに、common が 0.3%（budget の codex）ある。
  - Windows の表の「A と B の CI のプローブで同じ結果」: B のプローブ（run 44885833564）では、改行の無い引数が `.exe` に 32,516 文字、`.cmd` に 7,909 文字まで通った。
    A の「32,000 文字で 206」と食い違う。B は改行入りと標準入力を測っていない。
  - A の「モデル」の欄の「通常の呼び方と lean」: lean は m1 の haiku の 1 本だけ。
- 修正案: 数値を直す。Windows の表は「A の結果。B は改行の無い引数の上限だけを測り、`.exe` 32,516、`.cmd` 7,909」と出典を分ける。

### m2（Minor）: 12 件／90 秒は「品質ほぼ同じ」ではない。B では重複が減っている
- 根拠: A で比べたのは m1 の haiku の 1 本だけ。B では、12 件／90 秒の方がノードの数が 3 本とも少ない（121→89、98→95、114→92）。
  適合率も design と budget で上がった（0.314→0.427、0.408→0.442）。エッジの F1 も design で上がった（0.407→0.553）。下がったのは 1on1 のエッジの F1 だけ。
  M4 の主な問題（重複）に効いた設定は、測った中ではこれだけ。
- 修正案: 既定を 6 件／45 秒にする理由は「会議中の更新の遅れ」のままでよい。§3 と表の書き方は、データのとおり「呼び出しが半分になり、B では重複も減った」にする。
  S2 でも、この設定を整理の強化と並べて測る。

### m3（Minor）: 標準入力と `.cmd` の細部が、受け入れ条件に無い
- 根拠と修正案:
  - 標準入力への書き込みは、stdout / stderr の読み取りと並行に行い、書き終えたら閉じて EOF を送る。
    CLI がフラグの拒否などで先に終わったときの `BrokenPipe` は、終了コードで `non_zero_exit` に写す（`spawn` や I/O のエラーにしない）。
  - 起動の条件（§3）の「CLI が見つかる」と `is_available` も、同じ `.exe` / `.cmd` の解決を使う（今は `Command::new(binary)` のまま）。
  - Windows の CI のダミーの `.cmd` で、空の引数（`--tools ""`、`--setting-sources ""`）がそのまま届くことも確かめる。
    一時ファイルのパスに空白や日本語が入る場合（`C:\Users\山田 太郎\...`）も確かめる。
  - codex の `model_instructions_file` の値は TOML として読まれる（読めなければ文字列のまま）。PR #9 と同じく、`-C` のディレクトリに置いて相対名で渡すと、引用符とエスケープの問題を避けられる。

### m4（Minor）: 一時ファイルとして残ってよい中身を決めていない
- 根拠: §2 は「失敗・タイムアウトでも消す」とする。しかし、アプリが落ちたときや M1 の孫が残ったときの扱いが無い。
  system のファイルに文字起こしやノードの本文が入らないことも、明記していない（整理のプロンプトの組み立て方によっては入りうる）。
- 修正案: 「system のファイルには固定の指示とスキーマだけを書き、文字起こしやノードの本文は必ず標準入力で渡す」と §2 に書く。
  一時ファイルはアプリ専用のディレクトリに作り、起動時に残りを消す。

## 判定
converged: no（Blocker 0 / Major 4 / Minor 4 / nit 0）
