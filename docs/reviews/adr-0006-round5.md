## Findings

### M1（Major）: §8 の保存の照合は人の編集どうしの競合を検出せず、関数の入力も決めていないので、人が付けた根拠を黙って失いうる
- 根拠: §8「行の `based_on_rev` と `created_at` が画面で読んだものと同じことを確かめてから `body_json` を書き換える」。
  v0.15.0 の `save_analysis` は `created_at` を作り直し（upsert）のときだけ更新する（`store/analyses.rs` の `ON CONFLICT … created_at = strftime(…)`）。
  §8 の書き換えが `created_at` を変えないなら、画面が古い `body_json` を持ったまま 2 回目の編集を送ると照合は通り、
  画面の写しで本文ごと書き換える作りなら 1 回目の編集が消える（非同期の保存が 2 つ重なる、同じ分析を履歴と録音中の画面の両方で開く、など）。
  関数が「要素の鍵 + uid（付ける／外す）」を受けてトランザクションの中で読んだ本文に当てるのか、本文全体を受けるのかが書かれていない。
  前提の配列のどの要素かを指す鍵（`on` と順番など）も無い。
- 修正案: §8 の関数を「1 要素への操作（要素の鍵、uid、付ける／外す）を、同じ `BEGIN IMMEDIATE` の中で読んだ `body_json` に当てる」と決め、
  要素の鍵の形を書く。照合には編集ごとに変わる値（`edited_at` か版の整数）を足すか、操作の形にしたうえで「作り直しの検出だけに `created_at` を使う」と明記する。
  2b の受け入れ条件に「古い版からの 2 回目の操作が 1 回目を消さない」を足す。

### m1（Minor）: タスク 2b の目安「上位 3 件に 6 割」は、spike のデータでは当て推量と同じで、2-gram の良し悪しを測らない
- 根拠: r7 の (6) の誤り 52 件（A を除く。`results/r7/JUDGE.md` の `[list: …]`）で、各候補の入力の発話の数は 3〜30（i-notice は 3 件で、上位 3 件が全件）。
  入力の発話から 3 件を無作為に選んだときの期待の当たりは 31.6/52 = 61%。手元で、文字の 2-gram の共通数（空白を除く）で並べると、上位 3 件の当たりは 50/52（dd は 15/15）、
  1 位の当たりは 36/52 だった（スクラッチの使い捨てスクリプト。コミットしない）。つまり「6 割」は無作為でも届き、素朴な実装でも 96% になるので、合否も改善も見分けられない。
  実際の会議では入力の発話が 24,000 文字まで増えるので、spike の値は実際の当たりの目安にもならない。
- 修正案: 2b の測り方を「当たり（上位 3 件と 1 位）を、無作為の期待値（3/n）と並べて書く。発話が 8 件以上の候補だけの値も出す」にし、
  目安は無作為との差で置く（または目安を外して記録だけにする）。分母（52 件、`m2/g2` の 3 件の扱い）と、根拠の uid が複数あるとき（`u119/u120`）はどれかが入れば当たり、を書く。
  「未確認の前提」の 2-gram の行は、実際の会議の長い入力で確かめる、に直す。

### m2（Minor）: §8 の追加分が §1・§2・§5・「影響」に入っておらず、ADR 0007（CRT）に §8 が当たるかも書いていない
- 根拠: §1 は `stated` を付けられる者を「LLM の出力」と「アプリがグラフから写した要素」としか書いていない（人が §8 で付ける場合が無い）。
  §2 の表と §5 の出力の JSON に、`related`、`by`、入力の `uid` の一覧、「人が直した件数」の置き場所が無い（列なら、v0.15.0 で表はもう `CREATE TABLE IF NOT EXISTS` で出ているので、
  開発用の DB には列が足されず、ADR 0001 §1 の「表を足すだけなので移行は要らない」が崩れる）。「影響」の公開 API・保存形式は r5 のまま。
  ADR 0007 は「ADR 0006 §1〜§3・§6 に乗る」（0007:19）で、§8 は共通の節に入っていないが、§8 は §1 と §3 の本文の形を変える。
- 修正案: §1 に「人が §8 で付けた要素（`by: "user"`）」を足し、§2・§5 に追加のフィールドと件数の置き場所（`body_json` の中か新しい列か。列なら移行）を書く。
  §8 は v1 では対立解消図だけ（CRT は ADR 0007 で決める）と明記する。「影響」に §8 の関数を足す。

### m3（Minor）: §8 の取り消しと作り直し中の編集が決まっていない
- 根拠: 人が付けた根拠を外したとき、要素が `related` を保ったまま `inferred` に戻るのか、`by` を消すのかが書いていない。
  人が付けられる uid は 1 つだけか（`grounds: [選んだ uid]`）、2 つ目を足せるのかも無い。同じ題材の作り直しが動いている間（LLM の 10〜60 秒）に §8 で編集すると、
  §3 の保存（upsert）が後から上書きして編集が消える（確認の文言は作り直しを押す前の話）。「人が直した件数」が付けて外したときに増えるか減るかも無い。
  また行が無いとき（作り直しのグラフの再構築で `delete_session` が消した後）の文言が「分析が作り直されました」で、実際と合わない。
- 修正案: 外すと `inferred` に戻り `related` は残す、`by` は消す、と書く。同じ題材の作り直し中は §8 の操作を無効にする。件数は「付けた回数」か「今 `by: "user"` の要素の数」かを決める。
  行が無いときは「分析が消えました（グラフを作り直したため）」とする。

### m4（Minor）: 確定したプロンプト（r8）は判定しておらず、r8 の数え方の記録も無い
- 根拠: Q4 は「今のプロンプトで確定」で、PR #52 の head（1bc365c）のプロンプトは r8（da50124）のもの。表の値は r7 のもの。
  r7 で「かもしれない」を含む dd は 13 件あったが、r8/REVIEW.md では 0 件で、dd はどれも「…と考えられるから」などの作った制約になった
  （例: design・e2e-design/i5 の「同時にドキュメントを確認することはできない」は、r7 の JUDGE.md が挙げた u92「試験を流している間に目を通せそう」と食い違う型のまま）。
  (3) と (6) がどう動いたかは測っていない。r8 に JUDGE.md が無く、「0/66」の数え方（どの語で数えたか）はどこにも残っていない。
- 修正案: §「計測」に「確定版は r8。r8 は (1)〜(6) を判定していない。数字は r7 のもの」と明記し、r8 の数え方（grep の語）を `results/r8/` か ADR に書く。
  「実際の会議で見るもの」の「dd が両立しないと推測しないか」に、r8 で作った制約が増えたことを添える。

### m5（Minor）: 「人が直した件数」を (6) の率の目安にするのは下限にしかならない
- 根拠: §8「記録」と「未確認の前提」は、人が直した件数で実際の会議の (6) を見るとしているが、件数は人が気づいて直したものだけで、分母（述べられていたのに推測と出た要素の数）が無い。
- 修正案: 「(6) の下限の目安」と書くか、分母として `inferred` の要素の数と `related` の 1 位に人が付けた割合を併せて記録する。

### n1（nit）: 読み手の人数が根拠と合わない
- 根拠: 「r1〜r4 は 4 人、r6・r7 は 2 人」とあるが、r2・r3・r4 の JUDGE.md はどれも「2 人に分けて読み」。4 人は r1 と、r4 が r2・r3 の (6) を数え直したときだけ。
- 修正案: 「r1 は 4 人、r2〜r7 は 2 人（r2・r3 の (6) は r4 で別の 4 人が数え直した）」にする。

### n2（nit）: 22 候補のうち 4 件は同じ入力の重複
- 根拠: r1/JUDGE.md「`design` と `e2e-design` は入力（`results/prompts/`）がバイト単位で同じ」。独立した題材は 18 件。§「計測」の入力の行に無い。
- 修正案: 入力の行に「`design` と `e2e-design` は同じ入力（独立した題材は 18 件）」と添える。

### n3（nit）: 計画の行の残りが再現手順の後に浮いている
- 根拠: 336 行「満たさなければプロンプトと入力を直して測り直す。haiku は記録だけ。」が、再現手順の段落の続きの字下げで残っている。

## §5 とプロンプトの照合
PR #52 の head の `cloud-system.txt` と、§5 の書き方の規則（A は到達したい状態、B・C は要望で相手の案で満たせないもの、両方で満たせる要望は A へ、
前提は偽でありうる信念、反論は理由になる矢印にだけ、dd は必ず 1 件で具体的な理由・述べられていれば stated・無ければ inferred で打ち手に両立のやり方、
「両方はできない」だけ・対立を打ち消す文・会議についての文の禁止、打ち手は制約を外す変更、basis は役割と無関係、提案者の利点も名指しすれば根拠）は一致した。
矛盾は無い。PR #52 はまだ OPEN なので、この ADR は PR #52 のマージの後にマージする（§5 が main のプロンプトを指すため）。
