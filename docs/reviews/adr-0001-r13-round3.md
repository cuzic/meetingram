## Findings

### M1（Major）: 「議題は、案が対立する issue」が定義として書かれており、§1 と正解の大半に反する
- 根拠: 280 行は「議題は、案が対立する issue。グラフでは…」と議題そのものを定義している。§1（209 行）の定義は「親を持たない issue」。
  正解に当てはめると、案が 1 つ以下で `objects_to` も無いのに、正解では議題になっている issue が多い:
  - 60 分の会議: 正解の issue 60 本の**すべて**（どれも案 1 つと決定 1 つ）。
  - 短い会議: m1 の g3「A社への説明をどうするか」（案 1）、m2 の g4「来期の目標をどう設定するか」（案 1）、
    m3 の g3「ベンダーロックインをどう避けるか」（案 1）、1on1 の i3「読み合わせを誰に頼めるか」（案 1）。どれも確認の問いではない。
  2 行目（細かな問いは「確認の問いで、議題の条件に当たらないもの」）と合わせて読めば、「どちらでもない issue」は親を付けずに残る、と解釈できる。
  しかし 1 行目をそのままプロンプトに書くと、段 1 は position の数 1 の添え書きを見て、60 分の会議の 60 の議題を「議題ではない」と読み、
  親を付けうる。そうなると、2 回目で 0.983 あった 60 分の会議の再現率を落とす方向に働く。
  タスク 4b の (5)（「議題の条件に当たらない確認の問い」だけに親を付け直す）は、十分条件の読み方と合っている。食い違っているのは 280 行だけ。
- 修正案: 280 行を十分条件にする。例:「`responds_to` する position が 2 件以上ある、または `objects_to` を受けた position が付いている issue は、
  必ず議題とし親を付けない（ほかの議題の判断材料になる問いでも）。それ以外の issue も、確認の問いでなければ議題のまま」。
  §1 の定義（親を持たない issue）はそのまま。プロンプトの文面も、この書き方に合わせる。

### m1（Minor）: 進め方の issue は「承認・却下で人が却下する」としているが、確認の一覧に出ない見込み
- 根拠: 366 行は、残った進め方の issue を会議後の承認・却下で人が却下するとする。§5（400 行）の確認の一覧の対象は、確信度がしきい値（0.6）**より低い** `auto` のノードだけ。
  2 回目の m2 の n1「相手が今日話したいことは何か」は確信度 0.6 なので、一覧に出ない。
- 修正案: 「却下できる」ではなく「議題として残る（アウトラインに出る）」と書くか、段 1 で親を外した issue の確信度を下げる（または確認の一覧に入れる）と書く。

### m2（Minor）: 段 2 が `responds_to` を足して、細かな問いが議題の条件に当たっても、外す手段が無い
- 根拠: 段 2（369 行）は抜けたエッジの `add_edge` を返す。細かな問いに 2 つ目の position の `responds_to` を足すと議題の条件に当たるが、
  `remove_edge` は段 1 だけ。最終のグラフで規則に反する親子が残り、評価ではその下のノードが外れる。
- 修正案: 段 2 のプロンプトに「親を持つ issue に `responds_to` を足して議題の条件に当たるなら足さない」と書くか、残りうることを §計測で数える
  （3 回目の結果に、最終のグラフで議題の条件に当たる子の issue の数を出す）。
