# 設計（ADR と spike）

成果物は Accepted の ADR と、それを実装する Codex タスクの分割案。コードは書かない。

## 置き場所と番号

- アプリ（UI、要約・ヒントの使い方、図解、議論グラフ）: meetingram の `docs/adr/NNNN-<slug>.md`（0001 から）。
- コア（録音、STT、イベント、Rhai、要約の基盤）: meetingram-core の `docs/adr/NNNN-<slug>.md`（0015 から。
  0001〜0014 は 1on1-recorder から引き継いだリスク台帳で、形式が違う）。
- 両方にまたがるなら、主になる側に 1 本書き、もう一方からリンクする。

## 手順

1. **現状を読む**: 関係する ADR、コード、コアの設計資料（`design.md`、`docs/*.md`）。
   推測で書かず、ファイルと行で確かめる。
2. **論点を分ける**: owner が決めること（要件・優先度・費用・プライバシー）と、設計で決めること（実装の選択）を分ける。
   owner の論点は選択肢と推奨を添えて AskUserQuestion でまとめて聞く。実装の選択を owner に聞かない。
3. **数値は spike で取る**: レイテンシ、トークン数、費用、精度などの数値は、使い捨ての計測（spike）か出典から取る。
   spike は `spike/<topic>` ブランチか repo 外で動かし、結果と再現手順を ADR に書く。
   実在の会議の録音は使わない（合成データか owner が用意したもの）。
4. **ADR を書く**: [adr-template.md](adr-template.md) の形で。選択肢を 2 つ以上比べ、捨てた理由を書く。
   確かめられなかった前提には *(未確認)* を付ける。
5. **実装の分割を書く**: ADR の末尾に、Codex に渡す単位（1 タスク = 1 PR = 数百〜千行）の一覧を、
   依存順と受け入れ条件つきで書く。コアとアプリにまたがるなら、コア PR → タグ → アプリ PR の順にする。
6. **レビューを受ける**: ADR の PR（`docs/adr-NNNN-<slug>` ブランチ）を作り、独立したレビュアー
   （Agent ツールで新しいエージェントを起動し、`.claude/skills/review-pr` の手順を渡す）に敵対的レビューを頼む。
   Blocker/Major が 0 になるまで直してから Status を Accepted にし、マージする。
7. **Codex に渡す**: 分割の先頭から `.claude/skills/codex-task` で仕様にする。

## 判断の目安

- 既存の仕組み（Local Broker のイベント、Rhai の hook、`summarize` の Summarizer）に乗せられるなら乗せる。
  新しい仕組みを作るなら、乗せられない理由を ADR に書く。
- 録音・文字起こしを外部サービスに送る設計は、送る先・送る内容・保存期間を ADR に明記し、owner の承認を取る。
- 会議中に動く処理（文字起こし、ヒント、図の更新）は、遅延の目標と、失敗したときに録音を止めないことを書く。
