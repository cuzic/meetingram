題材はすべて合成の会議。対象は `r4/REVIEW.md` の 22 候補 × 3 回（sonnet だけ）= 66 回。
プロンプトは meetingram-core の `fix/cloud-prompt` @ f1cb002。r3 からの変更は次のとおり。
- `basis` を、b・c の選び方から切り離した（発話が中身を述べていれば stated）。
- 発話に制約が無いときの正直な dd（「両立を妨げる制約は会議で述べられていない」）を許した。
- dd の例を、料理の設備と人手の 2 種類にした。
- d への反論を c の、d2 への反論を b の手がかりにしてよいとした。

r1〜r3 の判定は `r1/`・`r2/`・`r3/JUDGE.md`。

## 判定のしかた

- 基準・dd の規則・基準のずれの直し方は r2・r3 と同じ。判定は Claude が 2 人に分けて読み、件数を `r4/REVIEW.md` と突き合わせた（前提 334 件、全回で一致）。
- **正直な dd**: 実質が「両立を妨げる制約は会議で述べられていない」の dd は、(3) の分母と分子から外した（偽でありうる信念ではないため）。
  代わりに、入力に両立を妨げる制約を述べた発話が無いか（OK）、有るのに空にしたか（逃げ）を確かめた。
- **(6) を足した**: `inferred` の A・B・C・前提のうち、入力の発話が実際にその中身を述べているもの（stated にすべきだったもの）。基準は (4) と同じ厳しさ。
  - 反論や心配の形で言われた要望も、中身を述べていれば数える。
  - r2・r3 も同じ規則で数え直した（読み手は別の 4 人）。
  - 境界の判定が多く、読み手による差は ±数件ある。
- **(4) の 2 つの読み方。** r4 の読み手 2 人は、(4) を新しい厳しい読み方（S）で付けた。案の提案者が言う売り込みや利点（「件数を付けたいです…見えます」「視線を取られずに済みます」「先に見たほうが速いかな」）は「案を支える事実」で、要望 c・b の根拠にならない、とする読み方。
  r1〜r3 の (4) と r2〜r4 の (6) は、利点や心配が要望の中身（X）を名指ししていれば、X を求める要望の根拠になる、という読み方（U）で付けている。
  - (4) を S、(6) を U で読むと、同じ発話を (4) では「要望を述べていない」、(6) では「要望を述べている」と扱うことになり、食い違う。
  - そのため **(4) の主の値は U で出し、S の値も併記する**。案についての事実だけで、要望の中身を名指ししない根拠（例: 見積額だけ）は、U でも F。
  - r3 の (4) の 4 件の不合格（m3/g1 の見積もり u68〜u70、m1/g4 の u141・u144）は、どれも要望の中身（予算内・跳ねない、レビュー）を名指ししているので、U では P になる。
- `m1/g4` を除いた値も r3 と同じく出す。

## 正直な dd の読み方

- 66 回中 50 回が「両立を妨げる制約は会議で述べられていない」。読み手 2 人とも、**逃げ（入力に制約があるのに空にしたもの）は 0 件**とした。
  - 制約が会議にある `one-on-one/i6`（u23「午後の一回」）では、3 回とも正直な文を使わず、u23 を `stated` の dd にした。r3 まで inferred だったものが直った。
  - 埋め草の dd（定義から真、B と C の対立の言い直し）は 19 件 → 0 件になった。dd の不合格は 1 件だけ（m1/g1 run3 の、D2 の欠点を dd に置いたもの）。
- ただし、図としての情報は減った。
  - dd の打ち手は 38 → 14 件。正直な dd には打ち手が付かないので、打ち手の総数も 100 件まで減り、打ち手 0 件の回が 10 回ある。
  - D と D2 が実は併用できる組（`one-on-one/i5` の会議直後と午後の中間、`one-on-one/i-break`、`design/i4` の一度だけの警告と件数）でも「述べられていない」で止まり、「併用できるなら対立は解ける」とは言わない。対立解消図としては、ここが一番役に立つ指摘のはず。
  - 自明な排他（`m1/g4`「承認ルールは 1 つ」、`budget/i2`「同じ金」）でも空にしている。これは定義から真の文を禁じた結果で、正しい。
- 正直な dd は、画面で「会議で確かめる候補」の先頭に出すと、問い（「この 2 案は本当に両立しないか」）として働く。表示の側で文言を足す余地がある（下の修正案 2）。

## プロンプトの次の修正案

1. **反論・心配・利点も stated の根拠になると書く**（失敗 1 への対処）。
   「発話が、ある案の利点や相手の案の困る点として述べていても、それが要素の中身（守りたいもの・避けたいもの）を名指ししていれば、その uid を grounds に入れて stated にする」と足す。
   (4) を S で運用すると決めるなら、逆に「案の利点を述べただけの発話は、要望の grounds にしない」と書き、(6) の規則もそれに合わせる。どちらに決めるかは owner の判断。
2. **正直な dd に、併用の可能性を書かせる**。「両立を妨げる制約が会議で述べられておらず、2 案を併用できそうなら『2 案は併用できる可能性がある』と inferred で書き、その併用を打ち手にする」と足す。正直さを保ったまま、図の一番の使いどころを取り戻せる。
3. **反論の発言の使い先を明示する**。「入力の objects_to の理由は、少なくとも 1 つの前提（d への反論は cd、d2 への反論は bd）に使う」と足す（失敗 6）。
