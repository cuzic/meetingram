## r2 の新しい失敗の追跡

1. **dd を書かない** → **直った**（0/66。全回ちょうど 1 件）。
   代わりに、理由の無いところに埋め草の dd を書くようになり、dd の不合格は 12 → 19 件に増えた（失敗 A）。
2. **dd の作った制約・型どおりの言い回し** → **形を変えて残る**。
   - 「1 回分」「一律」のような作った具体は減った。r2 の `one-on-one/i5` の「午後の休憩は 1 回分だけ」は、r3 では「休憩に使える作業の合間は限られ」になった。
   - 会議に無い制約は inferred になっている。
   - しかし「限られた…を取り合う」という別の型が広がった:「限られた監視の予算と人手を取り合う」（m3/g1 run1〜3）、「同じ限られた端末予算を取り合い」（budget/i2 run1・2）、「同じ参加者の時間と注意を取り合う」（design/i5 run3）。購入か借用か、SaaS かマネージドか、のような択一にまで当てはめている。
   - 料理の例（「同じ口」）を写したものは無い。「同じ欄」は、会議（u115）に根拠がある `e2e-design/i-notice` run3 にだけ出た。
   - 会議と食い違う制約は残る（design/i5 run1・3、e2e-design/i5 run1 の「注意を取り合う」と u92「試験を流している間に目を通せそう」）。
3. **打ち手が減る** → **さらに悪化**。265 → 187 → 129。0 件の回が 5、1 件だけの回が 17。
   付いたものの質は、前提を偽にするものが多い。ただし、前提でなく問題そのものを消すものが残る:
   - 「別の財源で補う」（budget/i-adjust の dd）
   - 「問い合わせ対応を当番から外す」（budget/i-metric の cd）
   - 「事前に資料を配る」（e2e-design/i5 run2 の cd）
4. **B・C の stated と inferred の正しさ** → **大きく悪化（r3 で最も重い後退）**。
   - B・C の `inferred` は 38 → 92/132 に増えた。そのうち読み手が「発言（uXX）がその要望を述べている」と確かめたものが 45 件（33 回）、裏づけになる発言があるものがさらに 4 件。
     - `m3/g2` の B（u109「障害を見逃すのが一番怖い」）
     - `budget/i-adjust` の B（u101）と C（u100）
     - `budget/i-metric` の B（u25）と C（u26）
     - `design/i-notice` run1 の B・C（u116・u117 にほぼそのまま）
     - `m1/g1` の C（u17・u68）
   - 新しい規則「相手の案でも満たせる賛成の理由は b・c にしない。そういう理由が無ければ inferred」を広く取りすぎ、会議の発言を元に書いた要望まで「推測」にしている。
   - 画面では「推測: 会議では述べられていない」と出るので、利用者に誤った印を見せることになる。
   - dd でも、会議で述べられた制約が inferred になっている（one-on-one/i6 run2 の u23「午後の確認は一回」、e2e-design/i-notice run3 の u115、m2/g3 の u119「人が全然足りない」）。
   - 逆向きの誤りも 4 件ある。`stated` の C の根拠が、要望ではなく D2 を支える事実になっている:
     - m3/g1 run2・3 の C の根拠が u68〜u70（マネージドの見積もり）
     - m1/g4 run2・3 の C の根拠が u141・u144（D2 への賛成）
     - これが (4) の 4 件の不合格。
5. **「…から」の一様な語尾** → **変わらず**（332/332）。プロンプトが求める形なので、不合格にはしていない。
6. **A が決める行為になる** → **直った**（0 回。(1) の不合格は `m2/g3` run1 の、A が B に寄った 1 回だけ）。

## r3 で残った失敗

A. **dd が埋め草になる**（19 件。r3 の不合格の 3 分の 2）。「必ず 1 件書く」に従い、理由が無いときに次のものを書く。

   - 片方の案の欠点:「12月10日までの時間と人手では同期機能を…確かめきれない」（m1/g1 run3）
   - 削減どうしの論理の逆転:「同じ不足する予算を取り合い、片方を残すにはもう片方を削る必要がある」（budget/i-adjust run1〜3。r2 では run1・3 だけだった）

B. **B が D の言い直しになる、または会議から離れる**（(2) の不合格 8 回）
   - 「時間帯を問わず、2人目の承認者の都合に左右されずにホットフィックスを出せるようにしたい」（m1/g4 run1〜3。D の仕組みの言い直しで、昼間に待つ話は会議に無い）

   - 「携帯を手元で使える状態にしておきたい」（one-on-one/i-break run1・2。D2 を否定しただけで、会議の誰も言っていない）

## プロンプトの次の修正案

1. **stated の判定を、b・c の選び方と切り離す**（後退 4 への対処。最優先）。
   「b・c の文の中身を述べた発話があれば、それが相手の案でも満たせる理由かどうかに関係なく、その uid を grounds に入れて stated にする。
   inferred にするのは、b・c の中身を述べた発話が入力に無いときだけ」と書く。「そういう理由が無ければ b・c は inferred で書く」の一文は外す。
2. **dd の埋め草をやめさせる**（失敗 A への対処）。
   「両立を妨げる制約が入力から見つからなければ、dd は『両立を妨げる制約は会議で述べられていない』と inferred で書き、打ち手は付けない」のように、正直な空の dd を許す形にする（必ず 1 件、は保つ）。
   アプリ側で、この定型の文を「会議で確かめる候補」の一覧の先頭に出せば、dd を確かめる問いになる。
3. **削減どうしの対立を例で示す**。
   「どちらの案も削る案なら、dd は『両方削るほどではない／両方削ると困る理由』を書く」と足す（budget/i-adjust の論理の逆転）。
4. **反論も b・c の材料にする**。「d への反論は c の、d2 への反論は b の手がかりにしてよい」と足す（失敗 B・C への対処）。
