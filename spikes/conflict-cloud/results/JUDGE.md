## 判定のしかた

- 1 回ずつ全要素を読んだ。甘く取らない（疑わしいものは F）。
- 判定の基準
  - (1) A が B と C の両方に仕える目的か。片側の言い直し、片方が寄与しない、題材とつながらない決まり文句、A 自体が手段、は F。
  - (2) B・C が要望か。D・D2 に「したい」を付けただけ、手段や機能を含む、両方の案で満たせて対立を生まない、B・C の取り違え、は F。回ごとに、B と C の両方が通ったときだけ P。
  - (3) 前提が偽でありうる信念か。前提 1 件ずつ判定する。争いのない事実、行動、矢印の言い直し（「A には B が欠かせない」「どちらか一方を選ばなければならない」）、同語反復、矢印の理由になっていないもの（相手の案の欠点など）は F。
  - (4) `stated` の要素（A・B・C・前提・打ち手。D・D2 は除く）は、根拠の発話のどれかがその中身を言っているか。話題に触れるだけ、「可能性」を断定に強めたもの、案の説明や問いかけだけ、逆の主張、根拠に無い主張の付け足し、は F。
  - (5) 同じ候補・モデルの 3 回で A の趣旨が同じか。
- 判定は Claude が 4 人に分けて読み、共通の基準で付けた。その後、件数を `REVIEW.md` と突き合わせた（`stated` は sonnet 281・haiku 275 で一致、前提の件数は 3 回分の数え違いを直した）。
- **dd の前提は付け直した。** 読み手によって判定が割れていたため（`design` と `e2e-design` は入力がまったく同じで、ほぼ同じ文に P と F が付いていた）、規則を 1 つにして全件を見直した。
  P になるのは、両立しない理由になる制約を書いたもの（「時間帯を問わず一律」「午後の確認は一回なので」「同じ欄を使う」「人手不足で両方は担えない」「手続き上」）。
  F になるのは、理由のない「1 つに絞る必要があり併用できない」「同時にはできない」、定義から真になるもの、決める時期の話。
  この見直しで sonnet は 19 件が P→F、3 件が F→P になり、haiku は 9 件が P→F になった。見直す前の sonnet の (3) は 311/372 = 83.6%。
- `design` と `e2e-design` は入力（`results/prompts/`）がバイト単位で同じ。出力は別の呼び出しなので、両方とも数えた。
- 入力は手で作った正解のグラフで、流し切り＋整理の後のグラフではない（`SUMMARY.md`）。抽出の誤りは入っていない。

## プロンプトの修正案（`cloud-system.txt`）

今の指示は、前提を「『…だから B には D が要る』の『…』」と 1 行で定義するだけで、矢印ごとに何を書くか、何を書かないかを示していない。
B・C の要望には「行動ではなく」とあるが、対立を生むことは求めていない。次の差し替えと追記を提案する。

1. **前提の書き方を矢印ごとに定義し、言い直しを禁じる**（失敗 1・2 に効く）。`assumptions:` の段を次に差し替える。

   ```text
   - assumptions: 各矢印の裏にある前提。偽でありうる信念を、理由の形で書く。
     ab:「A を満たすには B が要る」と考える理由。A と B だけで書き、D・D2 の話を入れない。
     ac: 同じく A と C だけで書く。
     bd:「B を満たすには D が要る（D2 では B を満たせない）」と考える理由。D2 が B を損なうという反論は bd に置く。
     cd:「C を満たすには D2 が要る（D では C を満たせない）」と考える理由。D が C を損なうという反論は cd に置く。
     dd:「D と D2 は同時に採れない」と考える理由になる制約（同じ時間・予算・人手・欄を取り合う、
       全員・毎回・全件に一律でなければならない、手続きで決まっている、など）。片方の案の欠点や、決める時期の話は dd に書かない。
     次のものは前提にしない: 矢印をそのまま言い直した文（「A には B が欠かせない」「どちらか一方を選ばなければならない」
     「同時にはできない」）、A・B・C の語を使い回して定義から真になる文、争いのない事実、行動や提案。
     その矢印に理由が書けなければ、その矢印の前提は出さない。
   ```

   例を 1 組ずつ添える（合成の題材で）。dd の悪い例「監視基盤は 1 つに絞る必要がある」→ 良い例「監視の設定を 2 つの基盤で二重に保つ人手がない」。
2. **B・C は対立を生む要望にする**（失敗 3 に効く）。`b:`・`c:` の行に足す。

   ```text
   B は D2 では満たせない要望、C は D では満たせない要望にする。D・D2 の中の手段や仕組み（上限を付ける、一覧に出す、借りる、など）を
   B・C に入れない。両方の案で満たせる要望は B・C にせず、A に上げる。
   ```

3. **A を具体的にし、片側に寄せない**（失敗 4 に効く）。`a:` の行に足す。

   ```text
   A は、B を満たすことと C を満たすことの両方がその手段になる目的にする。題材の問いの言葉で具体的に書き、
   「適切に扱う」「うまく進める」のような中身のない語にしない。B か C のどちらかと同じことを言い直さない。
   ```

4. **打ち手を絞る**（失敗 6 に効く）。`injection:` の行を差し替える。

   ```text
   - injection: その前提を偽にする変更。前提の文が「偽になった」と言える変更だけを書く。
     確認・見積もり・調査・先送り、D や D2 そのもの、D・D2 の細かな改良は打ち手にしない。書けなければ付けない。
   ```

5. **stated の条件を厳しくする**（失敗 5 に効く。主に haiku）。`stated:` の行に足す。

   ```text
   根拠の発話が、その要素の主張そのものを述べているときだけ stated にする。話題に触れるだけ、案の説明だけ、問いかけ、
   要素と逆の主張、「可能性がある」を断定に強めた要素は stated にしない（inferred にする）。
   ```

直したら、同じ 22 候補で sonnet を測り直す。特に dd（sonnet の 41% が不合格）と、`budget/i2`・`m2/g2`・`design/i4` の前提を見る。
